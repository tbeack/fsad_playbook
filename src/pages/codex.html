01 — Getting Started

Codex CLI Best Practices

From installation to agentic workflows with OpenAI's Codex.

Codex CLI is OpenAI's open-source coding agent — a terminal UI (TUI) that reads files, writes code, and runs shell commands in a sandbox. It defaults to gpt-5.5 and supports multiple model providers including OpenAI, Azure, Ollama, Bedrock, and more. If your team uses OpenAI models or wants multi-provider flexibility, Codex is the FSAD-compatible agent to learn.

Tool-Agnostic by Design

FSAD is a methodology, not a tool. While this playbook focuses on Claude Code, the same principles — spec-driven development, markdown layer, agentic workflows — apply to Codex, Gemini CLI, and other coding agents. This section helps teams that use Codex either as their primary tool or alongside Claude Code.

AGENTS.md: Project Instructions

▼

Codex merges instructions from multiple AGENTS.md files in a top-down hierarchy. Later files override earlier ones:

# Priority order (highest → lowest):
1. ~/.codex/AGENTS.override.md   # Global overrides (highest priority)
2. ~/.codex/AGENTS.md            # Global defaults
3. <repo-root>/AGENTS.md        # Project-level instructions
4. <cwd>/AGENTS.md              # Sub-directory specifics

Key differences from CLAUDE.md:

  • Override files — AGENTS.override.md takes highest priority, useful for personal preferences that override team defaults
  • Size limit — 32 KiB by default (configurable via project_doc_max_bytes in config.toml)
  • Disable flag — Skip with --no-project-doc or CODEX_DISABLE_PROJECT_DOC=1
Dual-Tool Teams

If your team uses both Claude Code and Codex, maintain both CLAUDE.md and AGENTS.md in the same repo. Keep shared conventions (tech stack, testing rules, coding standards) consistent across both files.

Running Both Tools

Many FSAD teams use both Claude Code and Codex. Keep a CLAUDE.md and AGENTS.md in your repo with shared conventions. Use each tool's strengths: Claude Code for Anthropic model quality, Codex for OpenAI model access and multi-provider flexibility. The FSAD workflow — spec → plan → implement → review — works identically regardless of which agent executes.

02 — Project Anatomy

Codex Needs 4 Things

The instructions, the skills, the guardrails, the context. Same principles as Claude — different file names.

Key Insight

Prompting is temporary. Structure is permanent. A well-organized project gives Codex context automatically — every session, every agent thread, every teammate.

Pillar 1: AGENTS.md = Repo Memory

▼

Contains WHY (purpose), WHAT (repo map), HOW (rules + commands). Codex reads this file automatically at the start of every session. The 4-level hierarchy lets you layer global defaults with project-specific overrides.

# AGENTS.md

## Project Overview
E-commerce API — Node.js + PostgreSQL. Handles product catalog,
orders, and payments.

## Tech Stack
- Runtime: Node.js 20, TypeScript
- Database: PostgreSQL 15 + Prisma ORM
- Testing: Vitest, coverage > 80%

## Commands
- `npm run dev` — start dev server
- `npm test` — run tests
- `npm run lint` — lint + format

## Rules
- Never modify migration files after they've been applied
- All API endpoints require authentication middleware
- Use Zod for request validation, not manual checks
Tip

Codex merges AGENTS.md from 4 levels: ~/.codex/AGENTS.override.md (highest) → ~/.codex/AGENTS.md → repo root → current directory. Max 32 KiB by default. For hooks and tool policies, the equivalent cascade runs through config.toml — add a requirements.toml at system/org level to enforce constraints users cannot override.

Pillar 2: .agents/skills/ = Reusable Expert Modes

▼

Turn common workflows into skills. Codex skills live in .agents/skills/ and use a SKILL.md file. Each skill can include scripts, references, and assets alongside the markdown.

# .agents/skills/code-review/SKILL.md

# Code Review

## Process
1. Check for security vulnerabilities (OWASP Top 10)
2. Verify error handling covers edge cases
3. Check test coverage for new code paths
4. Review naming conventions match project style
5. Verify no secrets or credentials in code

## Checklist
- [ ] No SQL injection vectors
- [ ] Input validation on all endpoints
- [ ] Tests cover happy path + error cases
- [ ] No console.log statements left behind

Pillar 3: .rules Files = Guardrails

▼

Codex uses the Shell Tool MCP with .rules files for deterministic guardrails — allowing, prompting, or forbidding specific shell commands. Models forget. Rules don't.

# .rules — Shell command policies

allow npm test
allow npm run lint
allow npm run build
prompt npm install *        # Ask before installing packages
forbid rm -rf *             # Never allow recursive delete
forbid git push --force     # Never allow force push
Important

Rules intercept execve(2) calls, so they know the full path of executed programs. This is more granular than Claude's hooks — you control command execution at the shell level.

Pillar 4: docs/ = Progressive Context

▼

Architecture overview, ADRs, runbooks. Don't bloat AGENTS.md — put detailed docs in files Codex can read when needed. Same pattern as Claude.

docs/
├── architecture.md        # System design overview
├── adr/                   # Architecture Decision Records
│   ├── 001-use-prisma.md
│   ├── 002-auth-strategy.md
│   └── 003-caching-layer.md
├── runbooks/              # Operational procedures
│   ├── deploy.md
│   └── incident-response.md
└── api/                   # API documentation
    └── endpoints.md

Codex discovers and reads these files on demand when working in related areas. The key is progressive context — only loaded when relevant.

Pillar 5: Local AGENTS.md for Risky Modules

▼

Place small AGENTS.md files near sharp edges. Codex sees gotchas exactly when working in that directory.

# src/auth/AGENTS.md

## Critical: Authentication Module

- NEVER modify the JWT signing key rotation logic
- Token refresh uses sliding window — do not change to fixed expiry
- Rate limiting is per-IP, configured in middleware (not here)
- All changes to this module require security review
- Test with: `npm test -- --grep "auth"`

Good candidates: src/auth/, src/billing/, src/persistence/, infra/

Setting Up MCP Connections via codex mcp

Codex uses the codex mcp CLI to manage MCP servers. For HTTP servers (Jira, Figma, Notion), use --url. For stdio servers (Azure DevOps, community tools), pass the command after --.

Tool search by default (rust-v0.142.2): Codex now uses MCP tool search by default when the selected model supports it — tools are discovered on demand rather than loaded all at once at session start. This speeds up startup with large MCP server inventories and improves tool discovery. If you need a server's tools always available without deferral, add "alwaysLoad": true to that server's entry in ~/.codex/config.toml.

Interactive MCP tool authentication (rust-v0.144.0): MCP tools can now request user authentication mid-session without any experimental opt-in flag — interactive auth flows (OAuth prompts, credential dialogs) are fully supported out of the box.

MCP 2026-07-28 protocol support (rust-v0.147.0, opt-in): adds paginated tool discovery for large server inventories, multi-round requests, and non-blocking server startup — Codex no longer waits on a slow-starting MCP server before the session becomes usable.

OAuth reauthentication recovery (rust-v0.148.0): MCP servers now recover after OAuth reauthentication without restarting Codex — re-run codex mcp login <name> mid-session and the server reconnects in place. Reauthentication failures report clearer errors about which server needs attention, servers can pin their own OAuth callback port, and dynamic HTTP header helpers are supported for servers that need per-request headers.

1

Add an MCP Server

Use codex mcp add to register a server. For hosted HTTP endpoints, use --url:

# HTTP server (hosted endpoint)
codex mcp add atlassian --url https://mcp.atlassian.com/v1/mcp

# Stdio server (local process)
codex mcp add ado -- npx -y @azure-devops/mcp your-org-name

# Stdio server with env vars
codex mcp add my-server --env API_KEY=xxx -- npx -y @some/mcp-server
2

Authenticate via OAuth

For servers that support OAuth, run codex mcp login. A browser window opens for authentication:

codex mcp login atlassian
3

Verify the Connection

Use /mcp inside the Codex TUI or codex mcp list from the terminal to confirm servers are connected:

# In the Codex TUI:
/mcp

# From the terminal:
codex mcp list
4

Manage Servers

Use codex mcp subcommands to manage your connections:

codex mcp list              # List all configured servers
codex mcp get <name>        # Show server details
codex mcp remove <name>     # Remove a server
codex mcp login <name>      # OAuth login for a server
codex mcp logout <name>     # Clear OAuth credentials
CLI vs. Config File

Use codex mcp add for quick setup — it writes to ~/.codex/config.toml automatically. Edit config.toml directly when you need advanced options like startup_timeout_sec, enabled_tools allowlists, or project-scoped servers (.codex/config.toml in trusted projects).

Codex Chrome Extension

OpenAI released a Codex Chrome extension (May 2026) that gives Codex direct browser access — a different integration model from MCP. Instead of routing through an API, Codex reads and acts on the current browser context.

Use the Chrome extension for web-based tools where you need direct page interaction (reading tickets, filling fields, navigating UI). Use MCP for tools with stable APIs — MCP is more reliable for structured data and automated pipelines. Both can be active simultaneously.

04 — Code Review

Built-in Code Review with /review

Codex includes a native code review command that analyzes diffs without modifying your code.

How /review Works

The /review slash command analyzes your current diff (staged and unstaged changes) and provides feedback on bugs, security issues, code quality, and style — without making any modifications to your files.

Usage

1

Start a Codex Session

Launch Codex in your project directory:

codex
2

Run /review

Type /review to analyze your current changes. Codex examines the diff and provides structured feedback:

# Review current working tree changes
/review

# Or ask for a specific review focus
"Review the changes in src/auth/ for security issues"
3

Act on Feedback

Review the findings and ask Codex to fix specific issues, or continue working on your own.

Review Isn't Only Manual (rust-v0.148.0)

/review is no longer the only path into review. Automatic review is enforced for managed models — under a managed configuration, review runs on its own rather than waiting for you to invoke it. Strict automatic review is also enforced for MCP tool calls, so tool invocations routed through MCP servers are reviewed before they proceed. Expect review to fire without being asked in enterprise and managed deployments.

Claude Code Comparison

Claude Code uses a multi-agent fleet for code review (multiple specialized agents in parallel). Codex's /review is single-agent by default but can leverage multi-agent threads if configured. Both approaches catch bugs — Claude's is more comprehensive, Codex's is faster for quick reviews.

05 — Building Skills

Turn Repeatable Workflows into Reusable Expert Modes

Codex skills are markdown-driven workflows stored in .agents/skills/ — each skill gets its own directory with a SKILL.md file.

What are Codex Skills?

Skills are markdown instructions that Codex follows when invoked. Unlike Claude's flat .claude/skills/ files, Codex skills use a directory structure: each skill has a folder containing SKILL.md plus optional scripts, references, and asset files.

Skill Directory Structure

.agents/skills/
├── code-review/
│   └── SKILL.md              # Skill instructions
├── deploy/
│   ├── SKILL.md              # Skill instructions
│   ├── scripts/
│   │   └── check-staging.sh  # Helper scripts
│   └── references/
│       └── deploy-checklist.md
└── estimate/
    └── SKILL.md

Example: Deployment Skill

Deploy Skill — SKILL.md

▼ 
---
name: deploy
description: Guided deployment to staging and production with smoke-test gates
model: gpt-5.5
---

# Deployment Skill

## Overview
Guided deployment to staging and production environments.

## Process
1. Run the test suite: `npm test`
2. Check for uncommitted changes: `git status`
3. Run the staging check script: `./scripts/check-staging.sh`
4. Build the production bundle: `npm run build`
5. Deploy to staging: `npm run deploy:staging`
6. Run smoke tests against staging
7. If smoke tests pass, deploy to production

## Safety Rules
- NEVER deploy directly to production without staging
- Always check the deploy-checklist.md reference
- Abort if any test or smoke test fails
Skill Frontmatter & Validation (rust-v0.148.0)

Codex parses model annotations in skill frontmatter — add model: to pin which model a skill runs on. Skill validation also rejects unfinished TODO placeholders, so a scaffolded SKILL.md must be filled in before it will load. The bundled skill-creator guide was tightened to match.

Best Practice

Start with one skill for your most repeated workflow. Codex skills can include shell scripts and reference docs alongside the markdown — use this for deployment checklists, migration procedures, or incident response runbooks.

06 — Guidelines

Lessons from Real-World Codex Adoption

Practical guidance for teams using Codex for spec-driven agentic development.

Prompting

Be Specific About What, Not How

Tell Codex what outcome you want, not the implementation steps. Let the agent choose the approach based on codebase context.

Provide Business Context

Include business requirements, constraints, and existing patterns. "We need a user preferences API because mobile users complain about notification noise" is better than "add a PATCH endpoint."

Use Tab for File References

Press Tab to fuzzy-search files by name (prefix with @). This ensures the right context is loaded and prevents Codex from searching in the wrong places.

Use /plan Mode First

For complex features, start with /plan. Let Codex analyze and propose before making changes. Review the plan, then let it execute.

Project Structure

Keep AGENTS.md Focused

Stay under the 32 KiB limit. Put detailed docs in docs/ for progressive context — don't bloat your project instructions file.

Use Skills for Repeatable Workflows

If you find yourself giving the same instructions across sessions, encode them as a skill in .agents/skills/.

Use Local AGENTS.md for Sensitive Modules

Place small AGENTS.md files near auth, billing, and infrastructure code. Codex sees the guardrails exactly when working in that directory.

Use /compact to Manage Context

Long conversations eat context. Use /compact to summarize the conversation and free up tokens for the agent to work with.

Anti-Patterns to Avoid

Over-Permissive Sandbox

Using danger-full-access outside of containers defeats the security model. Stick with workspace-write for development.

Bloated AGENTS.md

Stuffing every rule into AGENTS.md defeats the purpose. Keep it focused on high-level rules; use docs/ and local AGENTS.md for details.

Ignoring Session Resume

Codex saves sessions automatically. Use codex resume to pick up where you left off instead of re-explaining context from scratch.

Not Using /compact

Long conversations degrade agent performance. Use /compact regularly to summarize and free context tokens.

Project Trust & Managed Auth

As of rust-v0.147.0, Codex requires explicit trust before running in an unfamiliar local project — you'll be prompted to confirm the first time Codex operates in a new directory, similar to how project-scoped MCP servers and hooks already only load in trusted projects. Managed authentication restrictions are also enforced before credentials are used, not after, closing a window where an untrusted project could exercise credentials prior to the trust check completing.

Security Review

The sec-review-team skill is model-agnostic — it spawns Claude Code agents internally to run a multi-specialist security review, but its output (REPORT.md + FINDINGS.jsonl) is a workflow any team can adopt regardless of which CLI they use day-to-day. Codex teams can run the review via Claude Code and apply the fixes directly in their Codex workflow.

07 — Hooks

Hooks — Automation & Guardrails

Event-driven shell commands that fire deterministically at specific points in the agent loop. Models forget. Hooks don't.

Hooks inject scripts into Codex's agentic loop at named lifecycle events. Unlike instructions in AGENTS.md that the model may or may not follow, hooks always execute when their event triggers — making them ideal for audit logging, policy enforcement, and automated validation.

Generally Available — May 2026

Codex Hooks reached General Availability on 2026-05-14. They are production-ready with no feature flag required — [features] codex_hooks = true is the default and stable for use in production pipelines, enterprise environments, and automated workflows.

Hook Event Types

EventWhen it firesCan block?Claude Code equivalent
SessionStartSession begins or resumesNo — adds context onlySessionStart
UserPromptSubmitUser submits a promptYes (exit 2)UserPromptSubmit
PreToolUseBefore Bash, apply_patch, or MCP tool runs; hooks can inject additional context into the turn by returning a context field in JSON outputYes (exit 2 or deny JSON)PreToolUse
PermissionRequestWhen Codex seeks approval (shell escalation, network)Yes — allow / denyPermissionRequest
PostToolUseAfter tool completes (including failed runs)Yes (exit 2 — replaces output)PostToolUse
StopWhen a turn completesYes — can request continuationStop
PreCompactBefore context compaction runsYes (exit 2 blocks compaction)PreCompact
PostCompactAfter context compaction completesNoPostCompact

Configuration

Enable hooks with [features] codex_hooks = true (default). Define hooks inline in config.toml or in a separate hooks.json. Project-scoped hooks go in .codex/config.toml and only load in trusted projects.

Async and MCP-tool hooks (rust-v0.148.0): a hook can now run asynchronously — Codex fires it and continues the turn instead of waiting for it to finish — and a hook can invoke an MCP tool directly instead of shelling out to a script. Hook listings show each hook's execution mode, so blocking hooks are distinguishable from background ones at a glance. A hook that exceeds its timeout now has its entire process tree terminated rather than just the top-level process, so orphaned children no longer linger, and hook runtimes refresh after plugin changes.

config.toml hook syntax

▼ 
# ~/.codex/config.toml  (global) or .codex/config.toml (project)
[features]
codex_hooks = true

# Fire before every Bash call
[[hooks.PreToolUse]]
matcher = "^Bash$"

[[hooks.PreToolUse.hooks]]
type          = "command"
command       = "/usr/bin/python3 ~/.codex/hooks/check-command.py"
timeout       = 10
statusMessage = "Checking command safety"

# Fire after any apply_patch / Edit / Write
[[hooks.PostToolUse]]
matcher = "apply_patch"

[[hooks.PostToolUse.hooks]]
type    = "command"
command = "/usr/bin/python3 ~/.codex/hooks/audit-log.py"

Exit Code Semantics

Exit codeMeaning
0 + valid JSONProcess output per event schema (allow, deny, inject context, request continuation)
0 + plain textAppend as developer context (SessionStart, UserPromptSubmit)
0 + no outputPass-through — hook ran successfully, no action taken
2Block / deny; read reason from stderr; exact behavior depends on event type

Recipes

Recipe: Block dangerous shell commands (PreToolUse)

▼ 
#!/usr/bin/env python3
import json, sys, re

hook_input = json.load(sys.stdin)
command = hook_input["tool_input"].get("command", "")

if re.search(r"rm\s+-rf|sudo\s+rm|DROP\s+TABLE", command):
    print(json.dumps({
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "High-risk command blocked by policy"
        }
    }))
sys.exit(0)

Recipe: Detect API keys in prompts (UserPromptSubmit)

▼ 
#!/usr/bin/env python3
import json, sys, re

hook_input = json.load(sys.stdin)
prompt = hook_input.get("prompt", "")

if re.search(r"sk-[a-zA-Z0-9]{20,}|AKIA[0-9A-Z]{16}", prompt):
    sys.stderr.write("Possible API key or AWS credential detected in prompt\n")
    sys.exit(2)  # blocks the prompt submission

Recipe: Audit-log every tool call (PostToolUse)

▼ 
#!/usr/bin/env python3
import json, sys, datetime, pathlib

hook_input = json.load(sys.stdin)
log_entry = {
    "ts":      datetime.datetime.utcnow().isoformat(),
    "session": hook_input["session_id"],
    "tool":    hook_input["tool_name"],
    "input":   hook_input["tool_input"],
}

log_path = pathlib.Path.home() / ".codex" / "audit.jsonl"
with log_path.open("a") as f:
    f.write(json.dumps(log_entry) + "\n")

# Exit 0 with no output = pass-through
Claude Code Comparison

Codex has 8 hook event types; Claude Code has more (26 total events including SubagentStart, TaskCreated, FileChanged, PreCompact, etc.). Both use the same input-via-stdin / exit-code pattern. If you're migrating hook scripts, the core logic is portable — only the event names and JSON shape differ slightly.

Advanced Features for Power Users

Multi-agent workflows, hooks, plugins, permission profiles, Bedrock, session management, CI/CD, multi-provider models, and Codex Cloud.

Multi-Agent Workflows

▼

Codex supports multi-agent threads with configurable concurrency and specialized roles. The V2 multi-agent experience (opt-in) is now stable as of v0.145.0, with configurable per-agent models and reasoning levels.

# ~/.codex/config.toml
[agents]
max_threads = 6
max_depth = 1
job_max_runtime_seconds = 3600

Per-sub-agent model and reasoning (v0.145.0): Configure different models and reasoning effort levels for each sub-agent role in config.toml:

# Per-role model and reasoning overrides
[agents.worker]
model = "gpt-5.5"
reasoning = "medium"

[agents.explorer]
model = "gpt-5.5"
reasoning = "low"

Built-in roles:

  • default — Standard agent behavior
  • worker — Focused task execution
  • explorer — Read-only codebase analysis
  • monitor — Long-running observation (up to 1-hour windows)

Batch processing: spawn_agents_on_csv reads a CSV and spawns one worker per row — useful for bulk migrations and parallel test generation.

Rollout token budgets (v0.142.0): Configure a per-thread token budget to cap token usage across agent threads. When nearing the limit, Codex surfaces remaining-budget reminders; turns abort automatically when the budget is exhausted. Set in config.toml under [agents]:

# ~/.codex/config.toml
[agents]
rollout_token_budget = 100000     # abort turn when budget exceeded
rollout_budget_reminder_threshold = 0.8  # warn at 80% consumed

Interactive dashboard (rust-v0.149.0): Run codex agents to open an interactive dashboard for day-to-day management of running agent tasks — search, start, open, rename, and stop tasks, with configurable keyboard shortcuts. This is distinct from the [agents] config.toml settings above, which govern concurrency and per-role behavior rather than task management.

Vim Editing Mode

▼

Codex v0.129.0 adds modal Vim editing in the composer. Toggle it mid-session with /vim, or enable it permanently in config:

# ~/.codex/config.toml — enable Vim mode globally

In Vim mode the composer supports standard motions (hjkl, w/b/e, 0/$, dd, yy, p, visual selection), plus expanded change motions (cw, c$, cc) and character replacement (r<char>) (rust-v0.149.0). Session Management

▼

Codex saves sessions automatically. Resume previous work without re-explaining context. The redesigned resume/fork picker lets you select, resume, or fork any saved session in a single UI — no need to know the session ID upfront. Renamed threads appear as name (thread-id) in resume hints for easy identification, and you can paste text directly into the picker search box to filter sessions. Sessions can also be archived (/archive or codex archive) to protect them from accidental resume or fork — restore any time with codex unarchive. For permanent removal, use /delete or codex delete (confirms before deleting and cleans up subagent threads). (v0.136.0–v0.140.0)

As of rust-v0.146.0, you can pin important threads from the picker for quick access, open side conversations alongside your main thread, and switch between them without closing either. Forked threads now include paginated parent history and support temporary forks that don't appear in thread listings — ideal for exploratory side work. As of rust-v0.147.0, you can organize threads into persistent, manually ordered sections in the picker, and browse long transcripts incrementally instead of loading the full history at once. As of rust-v0.148.0, archiving and restoring moved into the picker itself — archive or restore a session without dropping out to codex archive / codex unarchive. You can also start drafting your prompt while the TUI is still initializing, with resume and fork progress shown during startup, and resumed sessions now restore their persisted working directory and approval policy rather than inheriting whatever the current shell happens to be using. As of rust-v0.149.0, codex queue sends a message to an existing local or remote session without switching into it; queued messages now reliably wake idle sessions, resolve duplicate session names more usefully, and preserve pasted or deferred command semantics.

Codex Access Tokens

▼

Codex access tokens let ChatGPT Enterprise workspace members run fully non-interactive Codex workflows without manual browser-based authentication. Tokens carry the user's ChatGPT workspace identity and are ideal for scripts, schedulers, and private CI runners that can't go through an OAuth flow.

Who can create tokens: ChatGPT Enterprise workspace owners must first authorize members to generate tokens via the workspace admin settings. Once authorized, members create tokens in their account settings and reference them at runtime.

# Set the access token via environment variable
export CODEX_ACCESS_TOKEN=your-token-here

# Non-interactive execution — no browser prompt
codex exec --approval-mode never "run all tests and report failures"

# Use in a CI runner (GitHub Actions example)
env:
  CODEX_ACCESS_TOKEN: ${{ secrets.CODEX_ACCESS_TOKEN }}
Treat Like an API Key

Access tokens grant full Codex execution rights under your workspace identity. Store them in secrets managers (AWS Secrets Manager, GitHub Secrets, HashiCorp Vault) — never commit to version control or log in CI output. Rotate tokens if exposure is suspected.

Use cases: nightly background refactors, automated spec-to-code pipelines, private on-premise CI runners that need Codex without a browser session. Pairs well with --approval-mode never permission profiles for fully autonomous runs.

Permission Profiles

▼

Permission profiles replace the old binary sandbox flags with named, reusable policies for filesystem and network access. Define them in ~/.codex/config.toml and apply with --approval-mode or default_permissions. As of rust-v0.146.1, cyber-capable models get safer automatic-review defaults out of the box, and the terminal interface explains permission changes as they happen instead of applying them silently.

Built-in ProfileFilesystemNetwork
:read-onlyRead everywhereNone
:workspaceWrite to project root; deny *.env / *.secretsRestricted
:danger-no-sandboxUnrestrictedFull

Define a custom profile:

# ~/.codex/config.toml
[permissions.myproject.filesystem.":project_roots"]
"." = "write"
"**/*.env" = "none"       # deny reads of .env files
glob_scan_max_depth = 3

[permissions.myproject.network]
enabled = true
mode = "limited"

# Apply as default
default_permissions = ":myproject"
Fail-closed paths (rust-v0.148.0)

Sandbox restrictions now fail closed on both Linux and Windows: if a path is explicitly denied — or simply unreadable — the agent is refused access rather than being allowed through. Managed deny-read rules are also enforced inside the Windows sandbox, so requirements.toml policies apply consistently across platforms.

Enterprise: requirements.toml

Admins can enforce which profiles are allowed and deny filesystem paths via requirements.toml — an admin-managed policy file that users cannot override. Install it at a system path or distribute via MDM.

Amazon Bedrock

▼

Codex has first-class Amazon Bedrock support via AWS SigV4 signing and standard AWS credential resolution. Useful for teams with existing AWS infrastructure or data-residency requirements.

# ~/.codex/config.toml
[model_providers.amazon-bedrock.aws]
profile = "my-aws-profile"   # or use env vars
region  = "us-west-2"

# Credentials via standard AWS env vars also work:
# AWS_PROFILE=my-profile AWS_REGION=us-west-2 codex

AWS account state (available models, quota) is surfaced to app clients. Pairs well with permission profiles to restrict what Bedrock agents can touch. In addition to standard AWS credential env vars and named profiles, aws login console-login credentials (from aws login profiles) are supported for Bedrock auth as of v0.130.0. As of rust-v0.147.0, cached web search and remote conversation compaction are also enabled for Bedrock deployments, bringing them to parity with the default OpenAI-hosted setup. As of rust-v0.148.0, Amazon Bedrock Runtime ships as a built-in provider — configure it with an AWS profile and region without hand-rolling a custom provider block, and route gpt-5.6 requests through Bedrock.

Plugins

▼

Codex plugins extend the agent with bundled tools, skills, and hooks. Browse the marketplace in the TUI or install from the CLI. Plugins can be scoped globally or to a trusted project.

# In the TUI: open the plugin marketplace
/plugins

# Install a plugin from the marketplace
codex plugin install <plugin-name>

# Remove a plugin
codex plugin remove <plugin-name>

# Share a plugin with your workspace
codex plugin share <plugin-name>

# Publish a plugin to the workspace marketplace (rust-v0.146.0)
codex plugin publish <plugin-name>

codex plugin sync

Plugin scoping:

  • Global (~/.codex/) — available in every session
  • Project (.codex/) — loaded only in trusted projects
  • Workspace-shared — install once, available to teammates via workspace share link; admin-disabled plugins are flagged in /plugins

Plugins can bundle skills (SKILL.md), hooks, and tool allowlists in a single installable unit. Plugin-bundled hooks are enabled/disabled via the plugin's configuration. As of v0.130.0, the plugin details view (accessible from /plugins) shows all bundled hooks alongside skills and tools. As of v0.131.0, plugin workflows gained marketplace CLI commands (codex plugin share, version-aware publish and checkout), clearer shared-workspace buckets, and plugin hooks are now default-enabled on install. As of rust-v0.143.0, remote plugins are enabled by default — the marketplace shows richer catalog rows with npm sources and visible remote/local version indicators. As of rust-v0.146.0, Agent Plugin manifests provide a structured declaration format for bundling agent capabilities into a plugin; the marketplace also connects to additional plugin sources including Amazon Bedrock and Claude Code, expanding the available plugin catalog beyond the default Codex marketplace. As of rust-v0.147.0, Agent Plugins can be installed in a portable format and searched across local, personal, workspace, and remote plugin catalogs — broadening discovery beyond the Global/Project/Workspace-shared scopes above.

Claude Code Equivalent

Codex plugins map to Claude Code's plugin system — both use a marketplace model with skill + hook bundling. The key difference: Codex plugins install via codex plugin install; Claude plugins install via claude plugin install.
