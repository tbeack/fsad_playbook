The Environment Around the Model

Harness Engineering

A reliable agent isn't a smarter model — it's a smarter environment. This section covers the discipline of engineering that environment: the boundaries the agent operates inside, the record of what it did, and the point at which it has to hand control back to a person.

01 — The Thesis

The Model Proposes. The Harness Decides.

Picture the usual response to an agent that keeps going wrong: rewrite the prompt, upgrade the model, hand it a wider context window. None of it sticks — decisions still get dropped, the wrong tool still gets reached for, checks still get skipped, the same failure loop still repeats. Blaming the model is usually a mistake. What's missing is rarely intelligence — it's the scaffolding the model is operating inside.

That scaffolding is what this section calls the harness — the part of the system that decides what the model gets shown, what actions it's permitted to take, what survives after the conversation ends, and where the run is required to stop and wait for a person. A model on its own can only propose; it has no way to grant itself permissions, remember past runs, or check its own work. Consider two deployments of the exact same weights: dropped into a bare chat window, the model can only converse. Wired into a coding environment with file access, a test suite, a sandboxed shell, and a review step before merge, that same model can carry a ticket through to a shipped pull request. Nothing about the model changed between those two pictures — the difference was built entirely by what surrounded it.

Where the industry converged on this

This isn't a niche opinion — it surfaces everywhere people build production agents. Anthropic's account of how Claude Code came together draws the same line: reasoning is the model's job, while a separate layer governs what it can see, act on, keep, and where it must halt. OpenAI landed on the identical lesson from a different angle while retooling Codex for agent-first work — early momentum stalled because the surrounding setup hadn't yet defined what the agent was and wasn't allowed to do, and things picked back up once each missing capability got a name and a way to check for it, rather than leaving the agent to somehow figure it out on its own. Both stories point to the same fix: a model failing over and over is a cue to examine what surrounds it, not to keep rewording the ask.

02 — The Seven Jobs

What a Production Harness Actually Does

Each job below is a distinct responsibility with its own failure mode if skipped. Click one open to see the worked example.

(a) Turn the request into a contract

▼

Turn the raw ask into a scoped spec before any tool call happens: a goal, the inputs it's allowed to use, what output counts as acceptable, hard constraints, and a concrete definition of done. Skip that step and an agent can drift into solving an adjacent problem — one it's happy to mark "complete" — without anyone catching the substitution until much later.

{
  goal: "Add pagination to the /orders endpoint",
  inputs: ["src/routes/orders.ts", "existing query params"],
  output: "PR with tests passing",
  constraints: ["no breaking changes to the response shape"],
  done_when: ["tests pass", "p95 latency unchanged"]
}

In this repo: this is what a task-detail file's Summary + Acceptance Criteria sections already are — a contract written before implementation starts, not after.

(b) Give the agent a map, not a manual

▼

An agent still needs to know how the project works, but dumping every doc into the context window every time isn't the answer. Keep a lean root guide that just points elsewhere — to an architecture reference, a testing reference, product and security rules, task-specific guides — and pull each one in only when the work at hand actually calls for it. A pointer costs almost nothing; a wall of pasted docs eats the budget you need for actual reasoning.

In this repo: a root CLAUDE.md plus per-pod and per-project CLAUDE.md files, each documenting only what's specific at that level — never repeating what a parent doc already covers.

(c) Expose the right tools inside the right environment

▼

A tool is less a convenience for the model and more a contract with the real world it reaches into — what it does, what it returns, how loudly it fails, and exactly how far its permissions extend. A well-scoped tool removes the guesswork before the model ever has to reason under uncertainty; a vague one forces the model to reconstruct, after the fact, what its own action actually did.

Read files

No approval needed — the default-safe action.

Run tests

Fine inside an isolated sandbox, never against production.

Write files

Confined to the task's own workspace or worktree.

Deploy or delete

Blocked until a person explicitly signs off.

(d) Externalize memory into durable state

▼

Don't treat the chat transcript as your durable record of what happened. Push the things that matter — task id, where the run currently stands, artifacts produced, decisions made, failures encountered, approvals still pending — into structured state that lives outside the conversation window. Do that, and whoever (or whatever) picks the work back up gets the real, current state of the task instead of trying to reconstruct it from a compressed summary of the chat. That's the difference between an agent that can be handed off, interrupted, or restarted cleanly, and one that can't.

In this repo: a task-detail file plus a checked-in todo.md entry — durable state that outlives any single session's context window.

(e) Add sensors before adding autonomy

▼

A model can only fix what it's actually able to see going wrong. Concrete signals — a test suite, a linter, a screenshot, a log line, a metric, a schema check — replace a vague "looks fine" with something that can actually be argued about. There's a division of labor worth keeping straight: something has to build the thing, something else has to test it, and a third party has to rule on whether that test result is convincing enough to move forward. The model only ever fills the first seat — the other two belong to the surrounding tooling and the harness's own judgment call.

Code

Tests, type checks, lint.

UI

Render, screenshot, visual inspection.

Research

Source check, contradiction check.

Data

Schema, range, and freshness checks.

In this repo: this is exactly what the adversarial AC-verification pattern does — a task isn't marked done because the implementing agent says so, it's done because an independent verifier produced evidence and a refuter failed to break it.

(f) Enforce permissions outside the model

▼

A model's job stops at recommending; whether that recommendation is allowed to run is a separate decision, made by policy rather than by the model itself — MODEL SUGGESTS → POLICY CHECKS → TOOL EXECUTES, always in that order and never collapsed into one step. That separation earns its keep exactly when the stakes are highest — money moving, data being deleted, another person on the other end of the action. When a single system both picks the move and clears itself to take it, nobody's left standing between the idea and its consequences — that's usually how an expensive mistake slips through unnoticed until it's too late.

(g) Record traces and recover locally

▼

A well-kept run leaves behind enough of a paper trail that someone who wasn't there could reconstruct it: how many attempts it took and what that cost, what got surfaced to the model and in what order the tools actually ran, what shifted in stored state, the verdict verification returned, and what ultimately got shipped along with a way to walk that decision back. No trace means every failure starts from zero next time; a good one means each failure teaches the harness something permanent.

In this repo: this is the role a session log plays — a durable record of what an agent actually did, independent of what it says it did.

03 — Instructions as Infrastructure

Say It Once as Guidance. Say It Again as a Check.

A rule written only in prose gets read once, then drifts out of practice. Encoding it twice is what makes it stick.

The guidance

A rule a person or agent can understand: "background jobs must go through the shared queue instead of calling the payments API directly." It carries the reasoning behind the boundary.

The check

A mechanical enforcement nobody can talk their way around: CI rejects the diff if a background job's code path touches the payments client outside the queue module. It holds regardless of who's writing the code.

Do this once and the fix outlives the person who made it — nobody downstream has to recall the war story, because the enforcement mechanism carries the memory instead. A repo hook that mechanically enforces a CLAUDE.md rule is this pattern in practice.

04 — The Bounded Loop

Retry Belongs to the Harness, Not the Model

Telling an agent to just keep trying isn't a strategy — it's the absence of one. A retry loop only earns trust once it has evidence gating each attempt, a hard cap on how many it gets, a cost ceiling, and somewhere to escalate when it runs out.

for attempt in range(1, 4):
    result = model.attempt_fix(state)
    evidence = harness.verify(result)
    if evidence.passes:
        return accept(result)
    state = harness.record_failure(state, evidence)

return requestHumanReview(state)  # 3 failed attempts, stop and escalate

Repairing the gap is the model's job; deciding whether it's earned another swing belongs to the harness. That division shows up in how Anthropic thinks about agents that run for hours or days — the work has to be broken into artifacts that outlive any single context window, and grading those artifacts has to fall to something other than the agent that produced them, or the grade means nothing. It's the identical logic behind never letting the person who wrote a change have the last word on whether it's correct.

05 — Failure-Driven Upgrades

Fix the Class of Failure, Not Just the Run

Most fixes stop at the run that broke. The more durable habit is mapping each failure to a category and closing that category for good — a one-off fix buys nothing next time; a system-level fix pays off on every future run that would have hit the same wall.

Missing context

Broaden what the map points to instead of pasting in more raw text.

Wrong tool

Rewrite its description or fix how it gets routed to.

Bad output

Tighten the contract or bolt on a check that catches it next time.

Repeated loop

Cap the retries and wire in an escalation path.

Unsafe action

Gate it behind an explicit permission check.

Lost decision

Write it down somewhere state actually survives, not just this chat.

Unknown failure

That's the signal to add tracing you didn't have before.

06 — Brain, Hands, History

Keep the Three Components Separate

A reliable agent is easier to reason about, debug, and evolve when three roles stay distinct.

Brain

The reasoning core — proposes moves, remembers nothing between calls on its own.

Hands

The execution surface — the sandboxed tools that actually touch files, tests, and the network.

History

The permanent log — every step captured on the way past, immune to the sandbox or the model being swapped out.

Killing the sandbox doesn't erase what happened, because the record lives outside it. Swap the model out entirely and the tools and policy layer don't even notice — they were never coupled to it. Resume a task days later and a fresh session can rebuild exactly where things stood from nothing but the stored artifacts and log. None of that holds up if a single piece of software is asked to reason, hold the files, gatekeep permissions, and keep the official record all at once — stacking every role onto one component erases the independence that made each check meaningful in the first place. A pod keeping a model's judgment walled off from the sandboxed tools it's handed is this exact idea, just applied to how a team gets put together.

The Change Receipt

The output alone tells you nothing about how it got made. Keep a small receipt alongside it instead, and four things become possible that weren't before: comparing one model version against another on equal footing, tracing a regression back to the change that caused it, producing something an auditor can actually check, and stopping a plausible-looking answer from concealing a process that was broken the whole way through.

{
  context_sources: ["CLAUDE.md", "orders.ts", "orders.test.ts"],
  policy_version: "v3",
  model_route: "claude-sonnet-5",
  tools_used: ["read", "edit", "run_tests"],
  test_results: { pass: 14, fail: 0 },
  human_corrections: 1,
  retries: 1,
  cost_tokens: 42000,
  accepted_artifact: "PR #206",
  rollback_point: "commit 47b7ffe"
}
07 — The Maturity Ladder

Start With the Smallest Harness That Closes the Loop

None of this is a license to build a full platform before shipping a single task. Begin with the leanest setup that can watch what happens, check it, and recover from a bad step — then add weight only as the risk of the task actually calls for it.

A quick, low-stakes task can get away with a single prompt and someone eyeballing the result afterward. Something that runs for hours, touches live files, reaches out over the network, and ends in an open pull request is a different animal and needs the full apparatus. The general rule: don't build more harness than the risk in front of you justifies — reach for the heaviest multi-agent pod setup only when the task's actual blast radius calls for it, not by default.

08 — Self-Assessment

The Harness Engineering Checklist

Work through this list before an agent touches anything that matters. A pile of "no" answers won't be rescued by upgrading the model — it just means the eventual failure costs more.

The Real Shift

A prompt engineer worries about the wording of the ask. A context engineer worries about what's loaded into view before the model answers it. A harness engineer goes one layer further and worries about the entire operating environment — the thing that turns a technically-correct instruction into an outcome you can actually trust.

The durable advantage

Next month's model release will make this month's obsolete, but a good tool, test suite, policy layer, or trace log doesn't expire the same way — it keeps compounding no matter which model sits behind it. That's where the lasting edge actually accumulates: not in whoever has the sharpest model this quarter, but in whoever built the sturdiest environment for it to operate inside. Naming that discipline is the whole point of this section.
