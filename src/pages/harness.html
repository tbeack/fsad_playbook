The Environment Around the Model

Harness Engineering

A reliable agent does not need a smarter model. It needs a smarter environment. This section covers the discipline of building that environment. It covers the boundaries the agent works inside and the record of what it did. It also covers the point where it must hand control back to a person.

01 — The Thesis

The Model Proposes. The Harness Decides.

Picture the usual response to an agent that keeps failing: rewrite the prompt, upgrade the model, give it a wider context window. None of it works. Decisions still get dropped. The wrong tool still gets picked. Checks still get skipped. The same failure loop still repeats. Blaming the model is usually a mistake. The model rarely lacks intelligence. It lacks the scaffolding it needs to work inside.

This section calls that scaffolding the harness. The harness decides what the model sees, what actions it may take, what survives after the conversation ends, and when the run must stop and wait for a person. A model on its own can only propose. It cannot grant itself permissions, remember past runs, or check its own work.

Consider two deployments of the same weights. Dropped into a bare chat window, the model can only talk. Wired into a coding environment with file access, a test suite, a sandboxed shell, and a review step before merge, the same model can carry a ticket through to a shipped pull request. The model did not change between these two pictures. The environment around it did.

Where the industry converged on this

This is not a niche opinion. It shows up everywhere people build production agents. Anthropic's account of how Claude Code came together makes the same point: reasoning is the model's job, while a separate layer governs what it can see, act on, and keep, and decides where it must stop. OpenAI reached the same conclusion from a different angle while rebuilding Codex for agent-first work. Early progress stalled because the surrounding setup had not yet defined what the agent could and could not do. Progress picked up once each missing capability got a name and a way to check it, instead of leaving the agent to work it out alone. Both stories point to the same fix: when a model fails again and again, look at what surrounds it. Do not just reword the prompt.

HARNESS ENGINEERING → designs the environment + controls
GRAPH ENGINEERING   → designs the flow + state transitions
LOOP ENGINEERING    → designs the iteration + feedback

The rest of this page follows these three layers in order. First, what the harness gives every node to work with. Then, how nodes connect into a flow. Then, how a single node improves itself through its own loop.

02 — Instructions as Infrastructure

Say It Once as Guidance. Say It Again as a Check.

A rule written only in prose gets read once, then drifts out of practice. Encoding it twice is what makes it stick.

The guidance

A rule a person or agent can understand: "background jobs must go through the shared queue instead of calling the payments API directly." It carries the reasoning behind the boundary.

The check

A mechanical enforcement nobody can talk their way around: CI rejects the diff if a background job's code path touches the payments client outside the queue module. It holds regardless of who is writing the code.

Do this once and the fix outlives the person who made it. Nobody downstream has to recall the story behind it, because the enforcement mechanism carries the memory instead. A repo hook that mechanically enforces a CLAUDE.md rule is this pattern in practice.

03 — The Task Contract

Write the Contract First. Not After.

A raw request is not a spec. Write down the goal, the boundaries, and what counts as done before the first tool call, not after.

Turn the raw request into a scoped spec before any tool call happens. State the goal, the inputs the agent may use, what output counts as acceptable, hard constraints, and a concrete definition of done. Skip this step and an agent can drift into solving a nearby problem instead. It will mark that problem "complete," and nobody will catch the substitution until much later.

A minimal contract needs five fields: goal, inputs, output, constraints, and done_when. A fuller contract adds two more fields. These matter once a policy layer or a reviewer needs to check the run, not just read its output. An identity field ties the run to a specific task record. An explicit allowed_actions list scopes the agent, not just tells it what to do.

{
  "goal": "Add pagination to the /orders endpoint",
  "constraints": ["no breaking changes to the response shape"],
  "identity": "task-cbp-512",
  "data": ["src/routes/orders.ts", "existing query params"],
  "allowed_actions": ["read", "edit", "run_tests"],
  "success_criteria": ["tests pass", "p95 latency unchanged"]
}

The allowed_actions field must survive contact with the CLI. A permission rule or a tool allow-list in Claude Code or Codex CLI enforces it at runtime. The model does not grant itself these actions by reading the contract and behaving well.

Caveat: no coding CLI ships a native "task contract" object. This shape is a convention that teams enforce through task templates and prompts, not a built-in schema any vendor supports directly.

In this repo: a task-detail file's Summary and Acceptance Criteria sections already do this. They are a contract written before implementation starts, not after.

04 — Context and State

A Map, Not a Manual. State, Not a Transcript.

What the agent is shown and what survives after it stops are two different jobs. Skip either one and it fails the same way.

An agent still needs to know how the project works. Dumping every doc into the context window each time is not the answer. Keep a lean root guide that points elsewhere: to an architecture reference, a testing reference, product and security rules, and task-specific guides. Pull each one in only when the work at hand actually needs it. A pointer costs almost nothing. A wall of pasted docs eats the budget you need for real reasoning.

# CLAUDE.md (root — under 100 lines, points elsewhere)
- Architecture: docs/architecture.md
- Testing: docs/testing.md
- Task convention: todo.md + CBP-### task files, docs/tasks.md
- Never repeat a rule the parent doc already states — only add what's specific here.

In this repo: a root CLAUDE.md plus per-pod and per-project CLAUDE.md files. Each file documents only what is specific at that level. None repeats what a parent doc already covers.

How long should a root file be? Practitioners converge on under 60 to 200 lines, tighter than the soft ceilings either vendor publishes. This is not an uncontested win, though. A controlled study from ETH Zurich and LogicStar found no statistically significant improvement in task success from instruction files. It also found a 20 to 23 percent cost tax from the extra tokens these files burn on every run. Treat a root guide as a hygiene practice worth doing well, not a guaranteed performance gain.

Do not treat the chat transcript as your durable record of what happened. Push what matters into structured state that lives outside the conversation window: the task id, where the run stands, artifacts produced, decisions made, failures encountered, and approvals still pending. Do this, and whoever or whatever picks the work back up gets the real, current state of the task. It does not have to reconstruct that state from a compressed summary of the chat. This is the difference between an agent you can hand off, interrupt, or restart cleanly, and one you cannot.

In this repo: a task-detail file plus a checked-in todo.md entry. This state outlives any single session's context window.

05 — The Capability Plane

Describe the Tool Well. Sandbox It Anyway.

A tool's description is part of its safety boundary, not documentation. No permission rule works without a sandbox behind it.

A tool is not just a convenience for the model. It is a contract with the real world the model reaches into: what the tool does, what it returns, how loudly it fails, and exactly how far its permissions extend. A well-scoped tool removes the guesswork before the model has to reason under uncertainty. A vague tool forces the model to reconstruct, after the fact, what its own action actually did.

Read files

No approval needed. This is the default-safe action.

Run tests

Fine inside an isolated sandbox, never against production.

Write files

Confined to the task's own workspace or worktree.

Deploy or delete

Blocked until a person explicitly signs off.

Tool description quality is its own factor, independent of the model behind it. Rewriting tool descriptions alone, with no model change, pushed Claude 3.5 Sonnet to state-of-the-art results on SWE-bench Verified. A thin wrapper forces the model to reconstruct intent on every call. A description that names its parameters and return shape precisely lets the model pick the right tool on the first try.

# Weak tool description                     # Strong tool description
list_contacts(query)                         search_contacts(query, fields=["email","company"])
→ thin wrapper — model must                  → high-leverage — consolidates a
  reconstruct intent itself                    multi-call workflow into one call

The same logic scales further with code-execution-as-tool-surface. Instead of exposing every API call as its own tool, give the model a code-execution environment and let it call a client library directly. One report measured a 98.7 percent reduction in tokens burned per task this way. Other teams have since reproduced this result independently. It is not a one-off benchmark artifact.

Neither layer works alone

Permission rules and an OS-level sandbox are not substitutes for each other. Both must be in place at once. A permission rule with no sandbox behind it is one clever prompt away from being ignored. A sandbox with no permission rules still lets the model do anything the sandbox allows, whether or not that is the right call for this task.

06 — Control + Trust

Model Suggests. Policy Decides.

A suggestion and a decision are different acts. The line between them must sit outside the model, or it is not a line at all.

A model's job stops at recommending. Whether that recommendation is allowed to run is a separate decision. Policy makes that decision, not the model: MODEL SUGGESTS → POLICY CHECKS → TOOL EXECUTES, always in that order and never collapsed into one step. This separation matters most when the stakes are highest: money moving, data being deleted, another person affected by the action. When a single system both picks the move and clears itself to make it, nobody stands between the idea and its consequences.

The checks that hold are the ones a model can never argue past, because they do not live in the model at all. They are the allowlist of what is permitted, the spend cap, the time/turn cap, the defined scope, the bounded blast radius, the kill switch, and the safe fallback for when a limit trips. These are hard boundaries. The harness enforces them, not the model. They hold even when the model is confident, plausible, and wrong.

This is not hypothetical

Three incidents trace back to the same gap: nothing outside the model was checking before the tool executed. Documented classes of sandbox-bypass exist in coding-agent tooling. In the Cursor and Supabase breach, a prompt-injected support ticket talked an agent into exfiltrating a customer's database through its own connected credentials. Three chained CVEs in the official Git MCP server combined into a full repository takeover.

// .claude/settings.json (illustrative)
{
  "permissions": {
    "allow": ["Read(**)", "Bash(npm test:*)"],
    "ask": ["Bash(git push:*)"],
    "deny": ["Bash(rm -rf:*)", "Write(.env)"]
  }
}

Rules like these live in a file the model can read but not rewrite mid-session. The check happens in the harness, after the model has already suggested an action and before any tool runs.

07 — Graph & Loop Engineering

From Implicit Loop to Explicit Graph

A flat, single-agent loop is the entire architecture, right up until the task needs branching, parallel work, a pause for human approval, or a retry with a real escalation path. Past that point, represent the work as an explicit graph of nodes and edges. Do not leave it as one long implicit loop that the model quietly re-runs on its own.

Not a Built-in Feature Yet

Neither Claude Code nor Codex ships a native graph-orchestration engine today. Claude Code's Workflow tool is a research preview, and it works only with TypeScript. Codex's equivalent, Symphony, exists only as an unmaintained reference spec. It has never shipped as a feature. Everything below is a design pattern to build with what you already have: subagents, hooks, and your own state. It is not a capability you turn on with a flag.

A Small Vocabulary

These seven terms come from graph orchestration in general. They describe almost any multi-step agent architecture, so you do not need a new diagram convention each time:

Node

One agent invocation: a subagent, a Workflow agent() call, or an externally-spawned instance.

Edge

A transition between nodes, either declared explicitly or left to the orchestrating agent's judgment.

Branch

A parallel()-style fan-out to more than one path at once.

Join

The barrier that waits on and merges branch outputs before continuing.

Cycle

A forced-continuation loop. For example, a Stop-hook that blocks exit until conditions are met.

Interrupt

A mid-turn cancel, or a hold for human approval.

Subgraph

A nested, delegated task tree, treated as a single node from the outside.

Loop Engineering: the Inner Cycle

Telling an agent to just keep trying is not a strategy. It is the absence of one. A retry loop only earns trust once it is gated behind evidence, capped at a fixed number of attempts, priced against a cost ceiling, and given somewhere to escalate once it runs out. In graph terms, this is a single cycle: a forced-continuation edge that re-runs the same handful of nodes. It has two named exits: a success test that accepts the result, and a stop condition that hands control to a human instead of letting the model try forever.

for attempt in range(1, 4):
    result = model.attempt_fix(state)
    evidence = harness.verify(result)
    if evidence.passes:
        return accept(result)
    state = harness.record_failure(state, evidence)

return requestHumanReview(state)  # 3 failed attempts, stop and escalate

Repairing the gap is the model's job. Deciding whether it has earned another turn through the cycle belongs to the harness. The same division applies to how long-running agents work across hours or days. Work breaks into artifacts that outlive any single context window. Grading those artifacts only makes sense if the grader is a different node than the one that produced them. A review node cannot be the same node as the one it reviews, or the grade means nothing. This is the same logic behind never letting the person who wrote a change have the last word on whether it is correct.

Independence Is What Makes the Graph Trustworthy

The same reasoning that shapes the loop shapes the whole graph. Keep the reasoning node, the execution node, and the state and log node independent, joined only by explicit edges, instead of folding all three responsibilities into one component. Killing the execution subgraph, the sandbox and the tool runner, does not erase what happened, because the record lives in a separate node outside it. Swapping the reasoning node for a newer model version does not touch the edges to the tool subgraph, because those edges were never coupled to which model sits behind them.

Resuming a run days later, a fresh graph instance can rebuild exactly where things stood from nothing but the stored state node and the log. It needs no memory of the original run. None of this holds if a single piece of software is asked to reason, hold files, gatekeep permissions, and keep the official record all at once. Stacking every role onto one node erases the independence that made each check meaningful in the first place.

Decompose by Context Boundary, Not by Job Title

When a task needs more than one agent, the tempting default is a role pipeline: a planner hands off to an implementer, who hands off to a tester, who hands off to a reviewer. Anthropic has named this pattern directly as an anti-pattern. In practice, these role-split pipelines burn more tokens on coordination than on the actual work, because every handoff means re-explaining context the previous agent already had. It behaves like a telephone game. Each retelling loses a little fidelity, and by the third or fourth handoff, the original intent has thinned out.

The more durable split is by context boundary. Give each subagent a self-contained slice of the problem it can own end-to-end: a module, a file set, or a bounded question, rather than a stage in somebody else's pipeline. A node in the graph should map to "what does this agent need to know to finish its own piece," not "which title does this agent hold."

On cost: teams often cite specific multipliers for how much more multi-agent orchestration costs versus a single agent, such as 3x, 10x, or 15x. Treat all of these numbers with caution. They come from different vendors measuring different baselines: different tasks, different models, and different definitions of "done." They do not reconcile into one number. The useful move is to track your own token spend per approach, instead of planning a budget around someone else's benchmark.

08 — Observe + Improve

See What Happened, Then Judge Whether It Was Good

Sensors and traces tell you what happened. A receipt makes that record checkable. A failure class closed here does not reopen on the next run.

Add Sensors Before Adding Autonomy

A model can only fix what it can actually see going wrong. Concrete signals, such as a test suite, a linter, a screenshot, a log line, a metric, or a schema check, replace a vague "looks fine" with something you can actually argue about. There is a division of labor worth keeping straight: something has to build the thing, something else has to test it, and a third party has to judge whether that test result is convincing enough to move forward. The model only ever fills the first role. The other two belong to the surrounding tooling and the harness's own judgment.

Code

Tests, type checks, lint.

UI

Render, screenshot, visual inspection.

Research

Source check, contradiction check.

Data

Schema, range, and freshness checks.

In this repo: this is exactly what the adversarial AC-verification pattern does. A task is not marked done because the implementing agent says so. It is done because an independent verifier produced evidence and a refuter failed to break it.

Record Traces and Recover Locally

A well-kept run leaves behind enough of a paper trail that someone who was not there could reconstruct it. That trail shows how many attempts it took and what that cost, what got shown to the model and in what order the tools actually ran, what changed in stored state, the verdict verification returned, and what ultimately shipped, along with a way to walk that decision back. No trace means every failure starts from zero next time. A good trace means each failure teaches the harness something permanent.

In this repo: this is the role a session log plays: a durable record of what an agent actually did, independent of what it says it did.

The Change Receipt

The output alone tells you nothing about how it got made. Keep a small receipt alongside it instead. It makes four things possible that were not possible before: comparing one model version against another on equal footing, tracing a regression back to the change that caused it, producing something an auditor can actually check, and stopping a plausible-looking answer from hiding a process that was broken the whole way through.

{
  "context_sources": ["CLAUDE.md", "orders.ts", "orders.test.ts"],
  "policy_version": "v3",
  "model_route": "claude-sonnet-5",
  "tools_used": ["read", "edit", "run_tests"],
  "test_results": { "pass": 14, "fail": 0 },
  "human_corrections": 1,
  "retries": 1,
  "cost_tokens": 42000,
  "accepted_artifact": "PR #206",
  "rollback_point": "commit 47b7ffe"
}

Fix the Class of Failure, Not Just the Run

Most fixes stop at the run that broke. The more durable habit is mapping each failure to a category and closing that category for good. A one-off fix buys nothing next time. A system-level fix pays off on every future run that would have hit the same wall. This is what feeding failure back into the design actually means: improve prompts, tools, routing, the graph, the loop, and the policy, not just patch the run.

Missing context

Broaden what the map points to instead of pasting in more raw text.

Wrong tool

Rewrite its description or fix how it gets routed to.

Bad output

Tighten the contract or bolt on a check that catches it next time.

Repeated loop

Cap the retries and wire in an escalation path.

Unsafe action

Gate it behind an explicit permission check.

Lost decision

Write it down somewhere state actually survives, not just this chat.

Unknown failure

That is the signal to add tracing you did not have before.

The gap: most teams can see what an agent did (89%) far more often than they can judge whether it was good (52.4% run offline evals, 37.3% online). A trace log is not the same thing as a verdict.

09 — Durable Runtime Substrate

Neither CLI Ships a Durable Runtime

Resuming a conversation is not the same as resuming a job. Crash-survivable, day-later, exactly-once work needs a substrate the harness has to build.

Neither Claude Code nor Codex ships native durable execution. Both can rehydrate a conversation transcript into a fresh process, and that is enough to pick a session back up after a restart. But rehydration happens at the session level, not mid-tool-call. Nothing checkpoints the state of an in-flight action. So "crash between the tool call and the log write," "resume a run a day later," and "guarantee a side effect happened exactly once" are all outside what either CLI provides on its own. A team that needs these guarantees generally reaches past the CLI or SDK and wraps it in an external job-queue-plus-checkpoint pattern, a general-purpose durable-execution engine, or a bespoke equivalent, instead of expecting the harness to grow one internally.

Scheduling

A queue decides what runs next and how many runs happen at once. Events trigger work instead of a human starting it, and a concurrency limit keeps ten queued jobs from becoming ten simultaneous API calls fighting over the same rate limit.

Durability

The harness checkpoints progress as it happens, not only at the end, so a crash mid-run resumes from the last checkpoint instead of from scratch. Replay reconstructs how a run got where it is, for debugging or for recovering from a bad checkpoint.

Resilience

Failures are expected, not exceptional. A transient error retries with backoff instead of failing the whole run, and a fallback path exists for when retries run out: a cheaper model, a cached answer, or a clean handoff to a human.

Side effects

An action with a real-world effect, such as charging a card, sending an email, or writing a row, needs to survive being attempted twice without happening twice. That means idempotency keys on the way in, and a compensating action ready if a partially-completed sequence needs to be unwound.

# claim-before-execute: avoids a crash-between-execute-and-log gap
idempotency_key = f"{task_id}:{tool_call_id}"
if not state_store.claim(idempotency_key):
    return state_store.get_result(idempotency_key)  # already ran — don't repeat

result = tool.execute(action)
state_store.record(idempotency_key, result)
return result

The same durability problem shows up wherever a human sits in the loop. An approval gate is not a bounded-latency request or response call. The person on the other end might answer in ten seconds, or not look at it for three days. So a durable pause has to actually release the process and the connection while it waits, not hold a thread or a socket open on the hope of a quick reply. A runtime that blocks on approval the same way it blocks on a fast tool call will eventually time out, leak a connection, or fail while waiting for a human who has not opened their laptop yet.

10 — The Maturity Ladder

Start With the Smallest Harness That Closes the Loop

None of this is a license to build a full platform before shipping a single task. Begin with the leanest setup that can watch what happens, check it, and recover from a bad step. Add weight only as the risk of the task calls for it.

From Ladder to Components

Each rung is not just a metaphor. It maps onto the seven components above, and onto the reference architectures the CBP-530 dossier surveyed. Climbing the ladder just means turning on more of those components.

Ladder level Components actually populated Closest reference architecture
Bare prompt, bare modelnoneNone
+ project guide + scoped toolsetContext+State, Capability PlaneSolo developer, single repo
+ structured state, test suite, capped retry loop+ Loop Engineering, Observe+ImproveSmall team with CI
+ enforced permissions, full tracing, recovery, human approval gates+ Control+Trust, Graph Engineering, Durable Runtime SubstratePlatform team / long-running crash-survivable build

A quick, low-stakes task can get away with a single prompt and someone checking the result afterward. Something that runs for hours, touches live files, reaches out over the network, and ends in an open pull request is a different case and needs the full apparatus. The general rule: do not build more harness than the risk in front of you justifies. Reach for the heaviest multi-agent pod setup only when the task's actual blast radius calls for it, not by default.

11 — Self-Assessment

The Harness Engineering Checklist

Work through this list before an agent touches anything that matters. A pile of "no" answers will not be fixed by upgrading the model. It just means the eventual failure costs more.

# Question
1Does the task have a concrete definition of done before the agent starts?
2Can the agent retrieve just the relevant project knowledge instead of the whole codebase?
3Would a new teammate know exactly what each tool promises and how it signals a failure?
4Could a bug in this run touch anything a real user depends on?
5If the conversation vanished right now, would the decisions made in it survive somewhere else?
6For the steps that matter most, is there proof beyond the model's own say-so?
7Does anything that cannot be undone wait for a person to say go?
8If a step keeps repeating, is there a hard ceiling on how many times before it escalates?
9If the run is interrupted, can it pick back up where it left off?
10Six months from now, could you explain why a specific tool fired at a specific moment?
11When a run fails, does that lesson get written into something durable, such as a test, a policy, or a tool's description? Or does it just fade after a conversation about it?
12If the result turns out to be wrong after the fact, is there a way back?
13If this task branches or fans out, is the flow an explicit graph (declared edges) rather than left to the model's turn-by-turn judgment?
14If a side effect, such as a write, a spend, or a message, gets retried, is it idempotent? Or could a retry duplicate it?
15If the process crashes mid-run, is there a checkpoint to resume from, or does the whole run restart from scratch?

The Real Shift

A prompt engineer worries about the wording of the request. A context engineer worries about what is loaded into view before the model answers it. A harness engineer goes one layer further and worries about the entire operating environment: the thing that turns a technically-correct instruction into an outcome you can actually trust.

The durable advantage

Next month's model release will make this month's model obsolete. But a good tool, test suite, policy layer, or trace log does not expire the same way. It keeps compounding no matter which model sits behind it. That is where the lasting edge actually accumulates: not in whoever has the sharpest model this quarter, but in whoever built the sturdiest environment for it to operate inside. Naming that discipline is the whole point of this section.
