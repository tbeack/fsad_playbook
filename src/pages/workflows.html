01 — Inside the Project Initialize-Context Skill

/project:initialize-context

This is how a project's context gets built. The skill explores your actual repos, classifies what it finds against platform defaults, and writes the docs. Click each phase.

Load the hierarchy

Skill reads the full context chain

  • Pick project (or auto-detect from path)
  • Read root CLAUDE.md → platform defaults
  • Read pod CLAUDE.md → shared architecture
  • Read project CLAUDE.md → current state
  • Assess what's populated vs. template stubs
The key concept: classification

Everything the skill finds gets classified against what the platform already defines:

conforms supplements overrides

Project docs never repeat what's in the parent docs. They only document what's specific to the project — additions and deviations.

Option A: deep repo exploration

Claude explores your actual code

Give it GitHub repo names. It launches parallel subagents that read package.json, tsconfig, component directories, state management imports, test configs, CI pipelines — and returns structured findings.

What repo exploration actually reads

Each repo gets its own subagent that reads:

package.json / *.csproj  → dependencies
src/ structure           → component organization
grep for @Global, Autoload, redux + UI + state
webpack.config / vite.config → build tooling
Dockerfile / CI.yml      → deployment
.storybook/              → design system presence
test configs             → testing patterns

Findings are merged across repos, deduplicated, and classified as conforms / supplements / overrides.

Option B: quick dump

Paste anything

Confluence pages, README excerpts, architecture notes, Slack threads. Claude structures and classifies against platform defaults.

What gets drafted 
architecture/README.md       → full architecture doc
design-standards/README.md   → UI patterns + conventions
CLAUDE.md architecture section → inline summary + diagram
CLAUDE.md design standards   → inline summary
Product overview + tech stack → if full setup mode
Architecture README includes

System overview and design principles. ASCII service diagram (auto-generated from findings). Per-service docs with repo links and tech stack. Data flow descriptions. External-dependencies table. Infrastructure and deployments. Cross-cutting concerns — classified as conforms, supplements, or overrides. Relevant ADR references.

Each section: Accept / Edit / Redo — same review loop as the spec skill.

Write & update
  • Writes architecture/README.md
  • Writes design-standards/README.md
  • Updates CLAUDE.md (targeted sections only)
  • Preserves existing content not in scope
  • Verifies all files after writing
Incremental by design

The skill detects which sections are already populated. Re-run it to update specific sections without overwriting previous work. A project's context builds up over time — each run adds to it.

Like the spec skill, it's a single markdown file in .claude/commands/. The entire project context initialization process — repo exploration, classification, drafting, writing — encoded in plain English.

02 — Inside the Project Create-Spec Skill

/project:create-spec

A skill is just a markdown file with instructions. Here's what this one does — click each phase to see the flow.

Regular context

The skill loads your world

  • Pick project
  • Pick pod
  • Read pod CLAUDE.md
  • Follow context chain upward
  • Read 2–3 existing specs for conventions
  • Detect author from git config
Why this matters

Before a single word is drafted, Claude has the full product context: architecture, services, design standards, platform fundamentals, and examples of how this pod writes specs. The skill does the context loading — the human doesn't have to.

Option A: brain dump

Paste anything

Meeting notes, Slack threads, Gong snippets, half-formed thoughts. Claude structures them into the spec template. You review section by section.

The key insight

Both paths converge on the same output — a structured spec with problem framing, competitive lens, use cases, architecture context, and acceptance criteria.

The skill's job is to solicit the right inputs and load the right context. Then it hands off to Claude's plan mode for the actual writing. We built the funnel. Claude does the work.

Option B: guided

Step-by-step questions

Claude walks through each section with targeted prompts. Probes for the right inputs: user analytics, customer feedback, competitive signals, success criteria.

Guided mode sections 
Problem / Description  → what + why inputs
Competitive Lens       → web search, pattern detection
Use Cases              → generated from context
Architecture           → auto-populated from CLAUDE.md
Preconditions          → flags, roles, regions
Acceptance Criteria    → 2–3 rounds of iteration
Future Scope           → planned / possible / out
Each section: review loop

Every section gets presented to you with three options:

looks good edit redo

The skill stays in the loop until you're satisfied. Competitive lens auto-searches the web. Architecture auto-populates from the context chain. You're directing — not writing.

Write & publish
  • Assembles full spec
  • Writes to pod/dir/specs/feature-name.md
  • Regenerates pod roadmap
  • Generates next steps (open PR, refine TODOs)
Then what?

Open a PR. Start coding. The spec and code evolve together from here. When the feature ships, clean up the spec as a record of what was actually built.

The entire skill is a single markdown file in .claude/commands/ — ~300 lines. It encodes the process in plain English. Anyone can read it, anyone can PR changes to it.

03 — Inside the Add-Task Skill

/add-task

A project-specific skill that encodes this repo's task-tracking convention — sequential numbering, todo.md entries, and the task-NNN.md template. Click each phase to walk the flow.

Read the tracker

Find the next task number

The skill opens markdown/to do/todo.md, scans every TASK-### already taken, and increments the highest by one. Always 3 digits with leading zeros.

TASK-037 → TASK-038
Capture the title

One-liner, no form

If the user ran /add-task <title>, that becomes the title. Otherwise the skill asks once and waits — no multi-field modal, no upfront ceremony.

Append the entry first

Single-line commit to the tracker

- [ ] `TASK-NNN` [Title] → [task-NNN.md](task-NNN.md)

Inserted before any Bug Details section, or at the end of the list. The entry lands before any details are gathered, so the task is already real.

One question at a time

No form-dumps on the user

The skill asks in sequence, and accepts "use your best judgment" as a valid answer at any step:

source summary assessment plan acceptance
Write the task file

Canonical template, every time

# TASK-NNN — [Task Title]

## Source
## Summary
## Assessment
**Location:** `[file path]`
## Plan
## Acceptance Criteria
- [ ] …
Why a template matters

Section names, em-dash in the heading, checkbox-style acceptance criteria — all the small formatting decisions that would otherwise drift across contributors. The skill encodes them once so every task file reads the same.

Location hint (**Location:**) keeps implementation grounded in a real file path from day one.

Report back

Three things, every time

  • The new task number
  • That the entry was added to todo.md
  • The path to the new task file
What this skill really is

Not a form. Not a tracker UI. Just a markdown file in .claude/skills/ that encodes one contributor's tribal knowledge — numbering scheme, filename conventions, interview order, section headings — so every future session produces identical output without anyone having to remember it.

Small skill, but it's the pattern: any repeatable workflow becomes a markdown file.

04 — Inside the Commit-Changes Skill

/commit-changes

The counterpart to /add-task. When a batch of tasks is done, this skill writes the CHANGELOG entry, bumps the version, and commits — in the exact sequence that keeps the artifact coherent.

Find the shipping set

Completed, but not yet in CHANGELOG

The skill reads markdown/to do/todo.md for items marked [x], then cross-references CHANGELOG.md to filter out anything already shipped. If the set is ambiguous — multiple newly-completed tasks, only some meant to go — it asks the user before writing a single line.

Detect the next version

Read the top of CHANGELOG

### vN — YYYY-MM-DD
↓
### v(N+1) — <today>

Explicit $ARGUMENTS (e.g., v24) override auto-increment. Today's date is pulled from context, never guessed.

Pull per-task summaries

For each shipping task, the skill opens task-NNN.md and extracts the title + 1–4 concrete, past-tense bullets. If a task file is missing or opaque, it stops and asks — rather than inventing changelog prose.

CHANGELOG.md — new block

Insert above the previous version

### vN — YYYY-MM-DD

**[Rollup line for multi-task batches]**

**[Task title] (TASK-NNN)**
- [Change bullet]
- [Change bullet]

Sub-tasks (e.g., TASK-005a) group under their parent. Single-task ships skip the rollup line.

README.md + HTML title

Two surgical edits

| Current version | v(N+1) |
| Date updated    | YYYY-MM-DD |

And the <title> tag in fsad-playbook.html — but only the live-version occurrences. Historical vN references in the playbook's own changelog section stay untouched.

Sanity-check the diff

Before anything is staged

git status
git diff --stat
CHANGELOG top renders clean README version matches no stray edits
Why verify before committing

The playbook is shared with engineering teams. A silent typo in the changelog or a version mismatch between README and HTML title ships to every reader and erodes trust in the artifact. The skill stops on any inconsistency instead of powering through.

Scoped stage — never -A

Only files the skill intentionally changed

git add CHANGELOG.md README.md \
        fsad-playbook.html \
        "markdown/to do/todo.md" \
        "markdown/to do/task-NNN.md"

markdown/ often contains WIP notes. Using git add -A would catch them by accident.

Commit, push, report

Match the project's message style

vN: <rollup> (TASK-NNN, TASK-NNN)

- TASK-NNN: <terse bullet>
- TASK-NNN: <terse bullet>

Then git push. If it's non-fast-forward, auth-fail, or hook-blocked — the skill stops and reports. No force-push, ever. Final message to the user: version shipped, tasks included, short SHA, push status.
