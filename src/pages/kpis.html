KPIs to Measure Impact

Key metrics to track adoption, productivity, and ROI of agentic development.

01 — FSAD Metrics

Measuring FSAD Success

What to measure to demonstrate the value of agentic development to your organization.

Highest Priority

Token Consumption by User

Track per-developer AI usage to identify adoption patterns and cost centers. High consumption with high output signals effective use; high consumption with low output signals coaching opportunities.

Total Monthly Epics / Tickets

Volume of work items completed, comparing pre- vs. post-FSAD adoption. Expect a meaningful increase as AI agents accelerate implementation cycles.

Total Monthly Story Points

Throughput measurement for sprint-over-sprint comparison. Track velocity trends after FSAD adoption to quantify productivity gains.

Total PRs / Commits

Development velocity indicator. AI-assisted workflows typically produce higher commit frequency with smaller, more focused changesets.

Maintenance vs. New Product Development

Breakdown of time and code produced by maintenance vs. new product development. Measures whether AI frees engineering capacity for innovation over sustaining work.

Total $ Spend by AI Tool

Cost tracking per tool (Claude Code, Codex, Cursor, etc.) for ROI analysis. Correlate spend against velocity and output metrics to demonstrate return on investment.

Other Metrics

AI Coding Tools WAU

Weekly Active Users across AI coding tools. Measures adoption breadth across the engineering organization.

Lines of Code Produced

AI-generated vs. human-written code split. Track the ratio over time to understand how AI contribution evolves.

AI Commits vs. Acceptance Rates

How often AI-generated code is accepted vs. revised. A quality signal — high acceptance rates indicate well-configured agents and effective specs.

Start Small

Don't instrument everything on day one. Token consumption + story points alone can demonstrate ROI within a single sprint. Add granularity as your FSAD practice matures and leadership asks deeper questions.

02 — Process Health

Process Health Metrics

Volume tells you how much work moved. Process health tells you whether it moved safely and fast. Pair a leading (speed) metric with a lagging (quality) metric for each stage of the workflow so a faster cycle time never gets read as progress on its own.

Leading Indicators — process speed

Spec → Plan Cycle Time

Elapsed time from the spec.md commit closing Phase 2 — Live Spec Session to the plan.md commit closing Phase 3 — Implementation Planning. A widening gap usually means the spec left decisions unresolved that the planning agent had to stop and ask about.

Plan → Merged PR Cycle Time

Elapsed time from plan approval at the end of Phase 3 to a merged PR at the end of Phase 5 — Human Review & Ship, spanning Phase 4 — Parallel Agent Execution. This is the true "idea to production" window agentic development is meant to compress.

First-Pass CI Success Rate

Share of agent-written changes from Phase 4 — Parallel Agent Execution that pass CI on the first run, with no human-triggered fix-up commit. A reliable proxy for spec clarity and agent-configuration health — low first-pass rates point back to Phase 2 or Phase 3, not to the agent.

Lagging Indicators — quality & outcome

PR Review Time

Human review duration during Phase 5 — Human Review & Ship. If review time climbs while PR size stays flat, treat it as a signal — not noise — that reviewers are compensating for spec drift or agent overreach upstream.

Defect / Vulnerability Escape Rate

Issues caught during Phase 5 review vs. found post-merge (production incidents, security findings). A rising post-merge share means the review gate isn't catching what agentic velocity now requires it to catch.

Repeat-Incident Rate

Share of incidents that recur in the same root-cause class within a fixed window (e.g. 90 days) despite a prior fix having shipped. High repeat rates mean the lesson learned isn't making it back into spec.md or plan.md for the next pass through the workflow.

Pair, Don't Isolate

Never report a cycle-time win without its paired quality metric alongside it. A faster Plan → Merged PR time achieved by cutting corners in Phase 5 review will show up later as a worse defect-escape or repeat-incident rate — track both so speed gains are real, not deferred.

03 — Token Optimization Strategies

Engineer the Economics, Not Just the Adoption

Adoption is no longer the open question — engineering orgs running FSAD at scale have already made agentic development the default. The next problem is system economics: how do you redesign the harness to produce more engineering output from the same, or less, machine intelligence?

Three Levers for Token Efficiency

Use Less Unnecessary Intelligence

Identify where the harness asks models to read, reason, iterate, or coordinate more than the task requires — over-agenting (multiple agents rediscovering the same problem), context that re-teaches the codebase instead of retrieving it progressively, loops that keep iterating past the point of measurable progress, and tickets sized for humans rather than agent-sized work packets.

Where are we paying multiple agents to rediscover or reconsider the same problem?

Don't Use Intelligence Where Software Will Do

Push deterministic work — compiler output, linting, dependency analysis, code search, test execution, schema validation, security scanning — outside the LLM loop. Reduce a 20,000-line build log to "12 failures → 3 root causes → 5 files" before an agent ever sees it. Tools perform computation and filtering; agents perform judgment.

What are we currently paying an LLM to read, discover, or calculate that ordinary software could determine deterministically?

Buy the Right Intelligence

Stop assuming frontier models should do most of the work. Explore a frontier-supervisor architecture — frontier intelligence decomposes and reviews, open-weight models execute bounded implementation — with escalation triggered by repeated failure, low confidence, or security risk rather than static task-type assignment.

Should frontier intelligence increasingly become the escalation path rather than the default execution layer?

Open-Weight Isn't Automatically Cheaper

The relevant comparison is not cost per million tokens — it's cost per successfully completed engineering task. Inference, infrastructure, retries, latency, engineer intervention, and quality failures all factor in. A weaker model that needs four attempts can end up costlier than a frontier model that succeeds on the first try, which is why hybrid-model experimentation matters more than a blanket cheaper-model switch.
