The default FSAD pod. One Product Manager, one UX Designer, and one Engineer work as a single unit — co-authoring the spec in real-time, with no handoffs. This covers the full spectrum of product intent, user experience, and technical execution in the smallest group that can make complete decisions.

Role Responsibilities
🎯

Product Manager

Owns problem statement, user stories, acceptance criteria, and success metrics. Frames the "what" and "why." Validates agent output against business intent.

🎨

UX Designer

Contributes interaction patterns, component choices, layout, and accessibility as structured markdown. Replaces the Figma-then-handoff pattern with inline design decisions.

⚙️

Engineer

Contributes architecture, data models, API contracts, and constraints. Orchestrates agents during execution. Reviews code quality and architectural coherence.

🤖

AI Agents

Consume spec.md and AGENTS.md to generate implementation in parallel via isolated git worktrees. Directed by the Engineer, constrained by the spec.

When To Use

  • User-facing features with both UI and backend work
  • New product areas requiring full alignment
  • Features where UX decisions impact architecture
  • Your default pod for standard product development

Key Artifacts

  • spec.md — Full feature spec with business, UX, and technical sections
  • AGENTS.md — Project-level agent instructions and guardrails
  • plan.md — Agent-generated implementation plan
  • tasks/*.md — Decomposed, parallelizable work units

The leanest FSAD pod. PM and Engineer work directly together when the feature is API-centric, backend-heavy, or follows established design patterns. Maximum speed — from spec to deployment in hours.

Role Responsibilities
🎯

Product Manager

Defines business requirement, API expectations, success criteria, and edge cases. Also makes lightweight UX decisions for admin interfaces or existing patterns.

⚙️

Engineer

Full ownership of technical spec, architecture, and agent orchestration. Co-authors spec with PM, then immediately enters plan mode and begins execution.

When To Use

  • API development, backend services, data pipelines
  • Admin/internal tools with standard UI patterns
  • Bug fixes and refactors with clear requirements
  • Rapid prototypes to validate feasibility

Superpower

  • Fastest spec-to-ship of any pod configuration
  • Minimal coordination — two people, one conversation
  • Ideal entry point for teams new to FSAD

Design-led for work where the UI is the product. UX Designer leads the spec; two engineers (frontend + backend) ensure the experience is technically achievable. PM role absorbed by UX for interaction-driven features.

Role Responsibilities
🎨

UX Designer (Pod Lead)

Leads the spec. Defines interaction models, animation, responsive breakpoints, component structure, and accessibility. Owns "what" and "why."

⚙️

Frontend Engineer

Translates UX decisions into component architecture and state management. Orchestrates frontend agents. Reviews rendered output against spec.

⚙️

Backend Engineer

Provides API contracts, data shapes, and performance guarantees. Orchestrates backend agents in parallel.

When To Use

  • Onboarding flows, wizards, multi-step journeys
  • Data visualization dashboards
  • Design system component development
  • Consumer-facing experiences where polish is differentiating

Key Artifacts

  • spec.md — UX-led with detailed interaction patterns
  • components.md — Component tree and state descriptions
  • api-contract.md — Backend data shapes
  • accessibility.md — WCAG checklist

Maximum-size FSAD pod for large, cross-cutting features spanning multiple services, requiring deep UX work and significant business risk. Two engineers split: one leads architecture, the other owns a specialized domain (security, performance, data).

Role Responsibilities
🎯

Product Manager

Owns business case, cross-team dependencies, and phased acceptance criteria for incremental shipping.

🎨

UX Designer

Full design authority. May produce lightweight wireframes alongside spec for large initiatives.

⚙️

Lead Engineer

Owns architecture, agent orchestration strategy, and cross-service decomposition.

⚙️

Specialist Engineer

Owns specialized domain — security, database migration, performance. Orchestrates own agent set in parallel.

When To Use

  • Features spanning multiple services or repositories
  • High-stakes initiatives (payments, auth, compliance)
  • Features requiring specialized expertise
  • Quarterly "big bets"

Watch Out For

  • Don't default to 4 — use only when complexity demands it
  • Two engineers must have distinct domains
  • If the pod feels slow, it's a Triad wearing a 4th person

Pure engineering pod for infrastructure, platform, and developer experience work. No PM, no designer. Two engineers co-author a technical spec. This pod handles the work that makes other pods faster — CI/CD, shared libraries, migrations, monitoring.

Role Responsibilities
⚙️

Engineer 1 (Architecture)

Owns system design, API contracts for internal consumers, and architectural decisions. Orchestrates agents for infrastructure-as-code and integration.

⚙️

Engineer 2 (Reliability)

Focuses on monitoring, alerting, performance testing, rollback strategies, and security. Reviews for production readiness.

When To Use

  • CI/CD pipeline work and deployment automation
  • Shared libraries, SDKs, internal tooling
  • Database migrations and schema evolution
  • Monitoring, observability, and security hardening

Key Artifacts

  • spec.md — Technical spec with Mermaid diagrams
  • adr/*.md — Architecture Decision Records
  • runbook.md — Operational runbook
  • perf-baseline.md — Performance benchmarks

Same Triad composition but in research mode. Not trying to ship — trying to find the right thing to ship. Spec is a hypothesis, agents build throwaway prototypes, output is a validated spec handed to a delivery pod. FSAD's answer to Dual Track Agile.

Role Responsibilities
🎯

Product Manager

Drives hypothesis. Defines customer problem, assumptions, and success criteria. Uses AI research agents for competitor analysis and customer synthesis.

🎨

UX Designer

Rapidly explores interaction models. Uses agents to generate multiple UI variants for testing with users.

⚙️

Engineer

Builds rapid throwaway prototypes. Validates technical feasibility. Explicitly not building production code.

When To Use

  • New product areas with high uncertainty
  • Exploring multiple solution approaches
  • Customer-facing prototypes for usability testing
  • Technical spikes to validate feasibility

Output

  • hypothesis.md — Problem hypothesis with assumptions
  • spec.md — Validated spec ready for delivery pod
  • prototype/ — Throwaway prototype
  • findings.md — What was learned and invalidated

Specialist engineering pod that builds the testing infrastructure used by every other pod — agents for test generation and code review, skills for coverage reporting, hooks for pre-commit and post-deploy verification gates, and MCP tools for fixture management. Its output is reusable tooling, not features.

Role Responsibilities
⚙️

QA Lead

Owns test strategy, verification gate standards, and acceptance criteria frameworks. Reviews agent-generated test output for coverage gaps. Defines the quality contract other pods must meet.

⚙️

Test Engineer

Builds custom agents, skills, hooks, and MCP tools for the team's testing stack. Maintains fixture libraries, regression suites, and test scaffolding.

🤖

QA Agents

Generate unit, integration, and e2e tests; run coverage analysis; perform spec-compliance validation; surface regressions across the codebase.

When To Use

  • Establishing QA infrastructure for a new product or team
  • Building custom test-generation agents and skills for specialized domains
  • Creating shared hooks and verification gates for CI/CD pipelines
  • Reducing testing tooling debt — standardizing test patterns across pods

Key Artifacts

  • test-plan.md — QA strategy, coverage targets, and acceptance gates
  • agents/ — Custom test generation, code review, and validation agents
  • skills/ — Coverage reporter, regression runner, fixture builder
  • hooks/ — PreToolUse / PostToolUse verification gates

03 — Pod Anti-Patterns

Compositions That Don't Work

🚫

The Solo Hero

One engineer doing everything. No second perspective means spec blind spots go unchallenged. Agents amplify mistakes at scale.

🚫

The Oversized Pod

5+ humans on a single spec. Communication overhead grows quadratically. Split into two pods with a shared API contract.

🚫

The Handoff Pod

PM writes spec → throws to designer → throws to engineer. Same sequential process. If you aren't co-authoring, it's not FSAD.

🚫

The Agent-Only Pod

Fully autonomous agents, no human review. Agent reliability is non-deterministic. Every pod requires human validation gates.

🚫

The Part-Time Pod

Members at 20% allocation across multiple pods. FSAD's speed comes from real-time collaboration. Async stalls the spec session.

🚫

The Duplicate Pod

Two engineers with identical skills. The second must own a distinct domain — otherwise use a Triad and let agents parallelize.

The Principle

Smallest Effective Pod.
Maximum Agent Leverage.

The right pod is the smallest group of humans who can make complete decisions about a feature without external dependencies — then direct an arbitrarily large fleet of agents to execute in parallel.
