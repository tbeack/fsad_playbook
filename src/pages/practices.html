08 — How to Get Started

From Zero to Spec-Driven Development

Six steps to adopt FSAD on your next feature. Each step builds on the previous one.

1

Start in Planning Mode

Use existing Figma mockups and PRDs as initial context. Feed Claude your existing documentation before writing new specs.

claude --conversation-mode plan
Tip

Plan mode is read-only — Claude can analyze your codebase and help write specs without modifying any files.

2

Create spec.md

Iterate with Claude until the spec covers everything needed to build. Include user stories, acceptance criteria, technical constraints, and UX decisions.

# Feature: [Name]

## Problem Statement
What problem are we solving and for whom?

## User Stories
- As a [role], I want [action] so that [outcome]

## Technical Spec
- Data model, API contracts, performance requirements

## UX Decisions
- Component choices, interaction patterns, responsive behavior

## Acceptance Criteria
- [ ] Criterion 1 — testable, specific
- [ ] Criterion 2 — measurable outcome
3

Build roadmap.md

Organize implementation into phases. Track what's done, what's next, and what's blocked.

# Roadmap

## Phase 1: Foundation ✅
- [x] Database schema
- [x] API scaffolding

## Phase 2: Core Feature 🔄
- [x] Backend logic
- [ ] Frontend components
- [ ] Integration tests

## Phase 3: Polish
- [ ] Error handling
- [ ] Loading states
- [ ] Accessibility audit
4

Build state.md

Track current project state for session resumption. What's been built, what decisions were made, current blockers.

# Project State

## Current Phase: 2 — Core Feature
## Status: In Progress

## Completed
- Database schema with migrations
- REST API endpoints (CRUD)

## In Progress
- Frontend form components

## Key Decisions
- Chose Zustand over Redux for state management
- Using server-side validation only (no client dupe)

## Blockers
- Waiting on design review for mobile layout
5

Break Into Phases

Each phase should fit within a context window. One phase = one focused area of work. If a phase feels too big, split it.

Tip

Context window limits are real. A phase that tries to do too much will result in agents losing track of requirements. Keep phases focused and atomic.

6

Create architecture.md

Describe overall architecture and tech stack. Include system diagram, data flow, and key dependencies.

Client (React) ──▶ API Gateway (Express) ──▶ Auth Service
                                           ──▶ Core Service ──▶ PostgreSQL
                                                             ──▶ Redis Cache
                                                             ──▶ Job Queue (Bull)
Best Practice

The document-driven workflow means your specs, roadmap, and state files ARE your project management system. No separate tool needed. Everything is version-controlled, diffable, and readable by both humans and agents.

Claude Needs 4 Things

Key Insight

Prompting is temporary. Structure is permanent. A well-organized project gives Claude context automatically — every session, every agent, every teammate.

▼

- Database: PostgreSQL 15 + Prisma ORM
- Testing: Vitest, coverage > 80%

- `npm test` — run tests

Example: A Production CLAUDE.md

▼

A real-world CLAUDE.md covering workflow orchestration, task management, and core principles. Copy and adapt for your team.

## Workflow Orchestration

### 1. Plan Mode Default
- Enter plan mode for ANY non-trivial task (3+ steps or architectural decisions)
- If something goes sideways, STOP and re-plan immediately — don't keep pushing
- Use plan mode for verification steps, not just building
- Write detailed specs upfront to reduce ambiguity

### 2. Subagent Strategy
- Use subagents liberally to keep main context window clean
- Offload research, exploration, and parallel analysis to subagents
- For complex problems, throw more compute at it via subagents
- One task per subagent for focused execution

### 3. Self-Improvement Loop
- After ANY correction from the user: update `tasks/lessons.md` with the pattern
- Write rules for yourself that prevent the same mistake
- Ruthlessly iterate on these lessons until mistake rate drops
- Review lessons at session start for relevant project

### 4. Verification Before Done
- Never mark a task complete without proving it works
- Diff behavior between main and your changes when relevant
- Ask yourself: "Would a staff engineer approve this?"
- Run tests, check logs, demonstrate correctness

### 5. Demand Elegance (Balanced)
- For non-trivial changes: pause and ask "is there a more elegant way?"
- If a fix feels hacky: "Knowing everything I know now, implement the elegant solution"
- Skip this for simple, obvious fixes — don't over-engineer
- Challenge your own work before presenting it

### 6. Autonomous Bug Fixing
- When given a bug report: just fix it. Don't ask for hand-holding
- Point at logs, errors, failing tests — then resolve them
- Zero context switching required from the user
- Go fix failing CI tests without being told how

## Task Management

1. **Plan First**: Write plan to `tasks/todo.md` with checkable items
2. **Verify Plan**: Check in before starting implementation
3. **Track Progress**: Mark items complete as you go
4. **Explain Changes**: High-level summary at each step
5. **Document Results**: Add review section to `tasks/todo.md`
6. **Capture Lessons**: Update `tasks/lessons.md` after corrections

## Core Principles

- **Simplicity First**: Make every change as simple as possible. Impact minimal code.
- **No Laziness**: Find root causes. No temporary fixes. Senior developer standards.
- **Minimal Impact**: Changes should only touch what's necessary. Avoid introducing bugs.

Pillar 3: .claude/hooks/ = Guardrails

▼

For deterministic actions: run formatter after edits, run tests on core changes, block unsafe directories. Models forget. Hooks don't.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "command": "npx prettier --write $file"
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Edit",
        "command": "echo $file | grep -v 'node_modules\\|dist\\|.env'"
      }
    ]
  }
}
Important

Hooks run shell commands automatically. Use them for formatting, linting, and safety checks — not for business logic. See the Hooks Deep Dive for configuration, exit codes, and more recipes.

09.5 — The Claude Configuration Cascade

How Teams Structure .claude/ Across Org, Project & Developer Layers

CLAUDE.md and .claude/ aren't just one file in one folder — they cascade. Org-wide rules, project-specific context, and personal preferences compose automatically as Claude walks up the directory tree. Here's how to architect the layers so team-shared rules stay in git, personal preferences stay local, and nothing gets duplicated.

The .claude/ directory (project layer)

.claude/ at project root · committed to git · shared with team

The project-level .claude/ folder is the control center for Claude Code. It defines instructions, custom commands, permission rules, and specialized agent behaviors for everyone working in the repo.

CLAUDE.md

Central instruction manual. Claude reads it at session start for project context, architecture, and coding standards.

settings.json

Permission controls — which tools (bash, read, write) are allowed, which files or commands are denied, which MCP servers are available.

rules/

Modular, markdown-based instructions. Rules without a paths field apply globally; others only when working in designated directories.

commands/

Custom slash commands (e.g. /project:review). Each markdown file becomes a command, with shell support via the ! prefix.

skills/

Reusable, context-aware workflows. More advanced than commands — auto-invoked by Claude when relevant, not just triggered manually.

agents/

Specialized subagents with defined personas and restricted tool access. Run risky tasks (reviews, audits) in isolated sessions.

The ~/.claude/ directory (user layer)

~/.claude/ · personal to each developer · never committed to git

The global folder holds personal preferences that apply across every project on your machine. It's yours alone — never mandate its contents across a team.

~/.claude/CLAUDE.md

Global coding preferences — "always use TypeScript", "prefer functional style", personal workflow quirks.

~/.claude/projects/

Auto-memory store. Claude persists MEMORY.md per project so knowledge survives across sessions.

commands/ & skills/

Personal commands and skills available everywhere, not scoped to one project. Your personal toolbox.

Org and project .claude/ live in git. Only ~/.claude/ stays local. The config-cascade rule

Cascading rules & precedence

CLAUDE.md files are loaded by walking up the directory tree from the current working directory. Multiple CLAUDE.md files combine — each layer adds context without requiring duplication. When rules conflict, precedence flows:

System policy  ─▶  User (~/.claude/)  ─▶  Project (.claude/)   ← wins
   (floor)         (personal prefs)        (team-shared, highest)

Project-level configuration takes highest precedence, ensuring team-shared rules always apply. System policy sets the safety floor. User preferences sit in between.

Path-Scoped Rules

Rules inside .claude/rules/ can declare a paths: field to apply only when Claude works in specific subdirectories (e.g. src/api/). Rules without paths apply project-wide. Use this to keep CLAUDE.md lean instead of overloading it with conditionals.

8 Recommendations for Teams

1. CLAUDE.md is your contract

Org-level sets non-negotiable rules. Project-level extends with domain context. The directory tree walk combines them automatically — never duplicate.

2. Use rules/ for path scoping

Don't overload CLAUDE.md with conditional logic. Put API rules in rules/api.md scoped to src/api/, test rules in rules/tests.md. Modular and clean.

3. Skills are portable packages

Encode repeatable workflows as SKILL.md directories. Any methodology becomes a mountable package any project can adopt. Skills auto-invoke — commands don't.

4. Agents isolate risky tasks

Define subagents for sensitive operations — code reviews, security audits, dependency checks. They run in isolated sessions with restricted tool access.

5. Commands are the team API

Slash commands (/project:review, /project:deploy) make workflows discoverable. Org commands set the floor; projects add domain-specific ones.

6. Let MEMORY.md accumulate

Claude auto-persists session knowledge to ~/.claude/projects/*/MEMORY.md. Let it build context over time and review periodically for accuracy.

7. Version-control shared layers

Org and project .claude/ live in git. Only ~/.claude/ stays local. Skills and agents are versioned and distributed like code.

8. Scope MCP servers per layer

Org settings.json defines shared servers (Slack, Drive). Projects add domain-specific ones. Users add personal tools. Servers compose additively.

Notable settings.json Keys

Beyond permissions and MCP server lists, settings.json accepts several useful configuration keys:

  • prUrlTemplate — Point the footer PR badge to a custom review URL instead of github.com. Still the answer for Bitbucket or GitHub Enterprise teams. As of v2.1.234, GitLab no longer needs the template for this: repos with a GitLab remote and an authenticated glab CLI get a native badge in the footer and statusline showing MR !N, with draft, pending, and green states.
  • otelHeadersHelper — Path to a script that auto-refreshes OTEL auth tokens (runs every 29 min). As of v2.1.193, the equivalent MCP headersHelper also re-runs and reconnects automatically when a tool call returns 401 or 403 — token expiry no longer requires a session restart. See Monitoring section.
  • disableAllHooks — Set true to disable all hooks globally (useful for troubleshooting).
  • allowManagedHooksOnly — When set to true, only hooks distributed via managed settings (MDM/org policy) are allowed to run; user-defined hooks in project and user settings.json are blocked. Useful for enterprise environments that want to control hook execution centrally.
  • requiredMinimumVersion / requiredMaximumVersion — Set via org managed settings to enforce a version range. Claude Code refuses to start if the installed version falls outside the range and directs the user to an approved version. Useful for enterprise compliance and rollout control.
  • skillOverrides — Control per-skill model visibility: {"skill-name": "off"} hides from both model and / menu; "user-invocable-only" hides from model only; "name-only" sends name without description to the model.
  • fallbackModel — Configure up to three fallback models tried in order when the primary model is overloaded or unavailable. Works in both interactive and print (-p) mode. Pairs with the --fallback-model CLI flag for session-level overrides. As of v2.1.247, sub-agents that fail on their first model call with a 404 also fall back through this same chain instead of dying outright, and the error surfaced to the parent session includes the error type, status, request id, and model.
  • settings.autoMode.hard_deny — Auto mode classifier rules that block unconditionally regardless of user intent or allow exceptions. Unlike regular deny rules (which the classifier can override when intent is clear), hard-deny rules are absolute. Use the same pattern array format as allow/deny rules in auto mode settings.
  • Auto mode built-in safety blocks — Auto mode blocks certain destructive commands by default, independent of your deny rules: git reset --hard, git checkout -- ., git clean -fd, and git stash drop are blocked unless you explicitly asked to discard local work; git commit --amend is blocked when the commit wasn't made by the agent this session; terraform destroy, pulumi destroy, and cdk destroy are blocked unless you named the specific stack. Use settings.autoMode.hard_deny for additional custom blocks (v2.1.183).
  • Containment Escape rule — Auto mode no longer auto-approves cloud metadata-credential fetches, egress evasion, or cross-tenant reach unless the environment explicitly marks them expected. Applies alongside settings.autoMode.hard_deny and the other built-in safety blocks (v2.1.257).
  • permissions.blockReadsOutsideWorkingDirectories — Auto mode now shows a one-time prompt before the first file read outside your working directories. Set this key to true to block such reads outright instead of prompting (v2.1.257).
  • autoMode.classifyAllShell — When set to true, routes all Bash/PowerShell commands through the auto-mode classifier, not just arbitrary-code-execution patterns. Use to tighten auto-mode coverage so every shell command is evaluated — at the cost of slightly more classification overhead (v2.1.193).
  • Auto mode reviews Monitor commands like Bash — Monitor tool allow rules are now set aside while auto mode is active, so Monitor commands go through the same auto-mode classifier review as Bash commands, instead of being auto-approved by a pre-existing allow rule (v2.1.236).
  • autoMode settings location — autoMode configuration (including classifyAllShell, hard_deny, and disableAutoMode) is not read from .claude/settings.local.json (the repo-resident, gitignored project-local file). Configure autoMode in ~/.claude/settings.json (user level) or the checked-in .claude/settings.json (project level) (v2.1.207).
  • autoMode classifier model for external sessions — In auto mode, the permission classifier that evaluates whether tool calls require approval defaults to Sonnet 5 for external sessions (SDK, webhooks, headless claude -p runs). The model is validated on the session's first request and pinned for the rest of that session — ensuring consistent, low-latency classification for unattended pipelines without incurring per-call model-selection overhead (v2.1.210).
  • Deny rule glob patterns — The tool-name position in deny rules now accepts glob patterns: "*" denies all tools. Allow rules reject non-MCP globs (only MCP tool name patterns are valid in allow rules). Unknown tool names in deny rules log a startup warning instead of being silently ignored.
  • Tool(param:value) permission rule syntax — Match a tool's input parameters in permission rules using Tool(param:value) syntax. Supports * as a wildcard value. Example: Agent(model:opus) blocks subagents from spawning with the Opus model. Works in allow, deny, and ask positions (v2.1.178).
  • disableBundledSkills — Set true to hide all bundled skills, workflows, and built-in slash commands from the model. Env var equivalent: CLAUDE_CODE_DISABLE_BUNDLED_SKILLS=1. Pairs with skillOverrides for per-skill granularity (v2.1.169).
  • wheelScrollAccelerationEnabled — Set false to disable mouse-wheel scroll acceleration in fullscreen mode. Default is true. Useful if the default acceleration feels too fast when scrolling long outputs (v2.1.174).
  • enforceAvailableModels — Enterprise managed setting. When enabled, the availableModels allowlist also constrains the Default model — a Default that would resolve to a disallowed model falls back to the first allowed model. User or project settings can no longer widen a managed availableModels list. Set via org/MDM managed settings only (v2.1.175).
  • language — Pin the language Claude Code uses when auto-generating session titles. Without this setting, titles are generated in the language of the conversation. Accepts BCP 47 language tags (e.g. en, ja, fr). Configurable at user or project level (v2.1.176).
  • footerLinksRegexes — Array of regex patterns for footer-row link badges. Strings in the session footer matching a pattern are rendered as clickable link badges. Configurable at user or managed (MDM/org) settings level (v2.1.176).
  • awsCredentialExport — Amazon Bedrock only. Path to a script or command that vends short-lived AWS credentials (e.g. via STS AssumeRole). Credentials returned by the script are now cached until their Expiration field rather than a fixed 1-hour TTL — reducing unnecessary re-auth cycles for tokens with longer lifetimes (v2.1.176).
  • attribution.sessionUrl — Set to false to omit the claude.ai session link from commits and PRs created in web and Remote Control sessions. Useful for teams that want clean commit attribution without embedding session URLs (v2.1.183).
  • respondToBashCommands — Controls whether Claude automatically responds to the output of ! (bang) bash commands. Default is true as of v2.1.186: Claude reads the output and replies in-turn. Set to false to restore the previous context-only behavior where ! injects shell output without triggering a reply (v2.1.186).
  • disableAutoMode — Set to true to opt out of auto mode on Amazon Bedrock, Google Vertex AI, and Foundry. Auto mode is now enabled by default on these platforms as of v2.1.207 (no longer requires CLAUDE_CODE_ENABLE_AUTO_MODE=1). Configure in user-level ~/.claude/settings.json or managed settings to keep manual permission prompts on cloud deployments (v2.1.207).
  • axScreenReader — Set to true to enable screen reader mode — plain-text rendering optimized for screen readers. Equivalent to the --ax-screen-reader CLI flag or CLAUDE_AX_SCREEN_READER=1 env var (v2.1.208).
  • vimInsertModeRemaps — Map two-key insert-mode sequences to special keys in vim mode. Example: {"vimInsertModeRemaps": {"jj": "Escape"}} lets you exit insert mode by typing jj quickly — a common vim muscle-memory shortcut (v2.1.208).
  • Permission rule startup warnings for Write / NotebookEdit / Glob — As of v2.1.210, Claude Code logs a startup warning when your permission rules contain Write(path), NotebookEdit(path), or Glob(path) entries. Use Edit(path) to match file-write operations and Read(path) to match file-read/glob operations in your allow/deny rules — these more specific names target the correct tools without matching unintended operations (v2.1.210).
  • workflowSizeGuideline — Set the advisory token-budget guideline for Dynamic workflow sessions (the "size guideline" shown to Claude when orchestrating large multi-agent runs). Configurable from any settings file (user, project, or managed). When set, the /config row for this setting is hidden from the config UI (v2.1.219).
  • crossSessionInbound — Controls whether cross-session messages sent to a session running with bypassed permissions are held for your approval before delivery. Pairs with the v2.1.224 cross-session SendMessage/ListAgents capability (see Power Usage → Agent Teams).
  • dialogExpiry — Sets how long a held cross-session message approval dialog stays pending before expiring. Messages to sessions without bypassed permissions auto-deliver regardless (v2.1.224).
  • spellcheck — Optional. Set to true to underline misspelled words in the prompt input as you type. Requires an aspell, hunspell, or ispell binary installed on the machine (v2.1.235).
  • keybindingFlavor — Deprecated as of v2.1.261. Previously set to "readline" to enable Bash-style word keys; as of v2.1.261 the Bash keybinding behavior is now the permanent default: Ctrl+W deletes back to whitespace, Alt+F / Alt+D stop at word end, punctuation separates words. The setting is ignored (introduced v2.1.238, deprecated v2.1.261).
  • modelPicker — Curate the /model picker with an ordered, labeled list of models (any id spelling, including Vertex/Bedrock ids) — append to or replace the built-in lineup (v2.1.243).
  • modelPricing — Managed setting: use an organization's contracted per-model rates and discount multiplier for /cost, the status line, and telemetry cost figures instead of list price. Configure via org/MDM managed settings (v2.1.243).
  • Bash allow-rule wildcard-before-subcommand warning — As of v2.1.246, Claude Code logs a startup warning for Bash permission rules with a wildcard positioned before the subcommand (e.g. Bash(git * main)), because such rules also match options inserted before the subcommand — unintentionally widening what the rule allows. Place wildcards after the subcommand (e.g. Bash(git commit *)) to scope the rule precisely.
  • feedbackDrafts — Set false to stop Claude from drafting a feedback report when something goes wrong in a session. When enabled (default), review and send the draft from /feedback (v2.1.247).
  • spinnerTipsOverride — Customize the tips shown while Claude works. As of v2.1.247, accepts an array of {id, text, cooldownSessions, priority} entries (rotate your own tips alongside the built-in ones, with cooldown and priority control), a tipsFile path to load tips from an external file, and a label to distinguish org-supplied tips in the UI.
  • managedMcpServers — Managed setting (org/MDM only): push HTTP/SSE MCP servers to every user — uses the same entry shape as .mcp.json. Entries that specify a command to run are skipped; only remote servers are delivered. Use deniedMcpServers (not allowedMcpServers) to block a managed server from loading — as of v2.1.259, allowedMcpServers governs only servers individual users add, not managed ones (v2.1.259).
  • bashOutputMaxChars / taskOutputMaxChars — Raise how much Bash command output (bashOutputMaxChars) and background-task output (taskOutputMaxChars) Claude receives inline before the rest is saved to a file; maximum is 128 000 characters each. Useful when large build logs or test output would otherwise be truncated (v2.1.261).
Permission Allowlists & settings.local.json

When you select "Always allow" at a Bash tool permission prompt, Claude Code writes that entry to .claude/settings.local.json — the gitignored, project-local layer. This means your personal approvals accumulate per-project without affecting teammates. To bulk-migrate common read-only patterns (grep, git diff, ls) into the allowlist at once, run /less-permission-prompts.

Patterns & Anti-Patterns

✕ Copying CLAUDE.md into every repo

Write once at the org level and inherit via the directory tree walk. Duplication guarantees drift.

✕ Domain rules at the org level

Keep domain context at the project level. Org level is for cross-cutting standards only.

✕ One 2000-line CLAUDE.md

Factor into rules/ with path scoping for modularity. Bloated CLAUDE.md files lose important rules in the noise.

✕ Mandating personal ~/.claude/

Let developers own their personal layer entirely. Enforcement belongs in the project .claude/, not the user's home.

✕ Running sensitive tasks in the main session

Define isolated agents/ with restricted permissions for audits, deploys, and anything touching credentials.

✕ Ignoring MEMORY.md

Stale auto-memory poisons future sessions. Periodically review for accuracy and prune drift.

External Memory: Obsidian & Markdown Vaults

Claude's MEMORY.md is passive — session knowledge auto-persists as the model works. A curated markdown vault (Obsidian, Logseq, plain notes/) is the complement: intentional, human-authored, and portable across tools, models, and years.

Andrej Karpathy popularized this pattern — a long-lived Obsidian vault of notes, decisions, and research that gets selectively fed into LLM sessions as high-signal context. The vault outlives any single model or IDE; the AI is just one of many readers.

Practical integration patterns:

  • Symlink a vault subfolder into the repo (e.g. docs/notes/ → ~/Obsidian/project-x/) so Claude reads it as part of the project tree.
  • Paste relevant notes into context at session start — curated beats comprehensive.
  • Wire an Obsidian / Reflect / Notion MCP server so Claude can search and append notes directly, turning the vault into a read/write memory layer.
  • Treat the vault as source-of-truth; let MEMORY.md churn freely underneath it.
Codex Equivalent

OpenAI's Codex CLI uses the same layered architecture with different filenames: AGENTS.md instead of CLAUDE.md, .rules/ for guardrails, and .agents/skills/ for reusable workflows. The cascade model (org → project → user) is identical. See the Codex Best Practices page for the full mapping.

12 — Best Practices & Guidelines

Lessons from Real-World FSAD Adoption

Practical guidance for teams adopting spec-driven agentic development.

Background Context Matters

Avoid over-emphasis on technical capabilities. Insufficient business context hurts initial coding sessions. A holistic approach beyond engineering-only specifications yields best results. Include background details, business context, problems to be solved, and design systems.

Prompting

Be Specific About What, Not How

Tell Claude what outcome you want, not the implementation steps. Let the agent choose the approach based on codebase context.

Provide Business Context

Include business requirements, constraints, and existing patterns. "We need a user preferences API because mobile users complain about notification noise" is better than "add a PATCH endpoint."

Use @ References

Point Claude at specific files with @filename. This ensures the right context is loaded and prevents the agent from searching in the wrong places.

Use Plan Mode First

For complex features, start with --conversation-mode plan. Let Claude analyze and propose before making changes. Review the plan, then execute.

Project Structure

Keep CLAUDE.md Concise

Under 100 lines. If it's too long, Claude may miss critical rules. Move detailed docs to docs/ for progressive loading.

Use Local CLAUDE.md Files

Place module-specific rules near the code they protect. src/auth/CLAUDE.md gets loaded when Claude works in that directory.

Organize docs/ for Progressive Context

Architecture overview, ADRs, and runbooks in docs/. Claude reads them when relevant, not every session.

Version Control Your Prompts

Specs, skills, and configuration are code. Commit them. Review changes in PRs. Roll back if something breaks.

Workflow

Use /clear Between Tasks

Reset context between unrelated tasks. Stale context from a previous task can mislead agents on the current one.

Use /compact When Context Gets Large

Compress conversation history to free up context window space for the current task. Especially useful in long sessions.

Commit Frequently

Small, atomic changes. Each commit should represent one logical unit of work. Makes it easy to revert if an agent goes off track.

Review Agent Output Before Shipping

Agents produce consistent code from specs, but they can hallucinate or over-interpret. Human review is non-negotiable.

Todo Tools Are Opt-In on Newer Models

TaskCreate, TaskUpdate, TaskList, and TodoWrite are no longer available by default on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and newer models (v2.1.233). Set CLAUDE_CODE_ENABLE_TODO_TOOLS=1 to restore them.

Common Pitfalls

Jumping Straight to Code

Without a spec, agents guess at requirements. The result is wasted cycles and code that doesn't match what was needed.

Technical Specs Without Business Context

"Add a PATCH endpoint" tells the agent what to build but not why. Missing context leads to wrong trade-offs.

Not Using Plan Mode

For complex features, jumping straight to implementation means no opportunity to catch misunderstandings before they become code.

Ignoring Context Window Limits

Overloading a session with too many files or too large a scope causes the agent to lose track of requirements mid-task.

Not Reviewing Agent Code

Agents are powerful but non-deterministic. Code that passes tests can still have logic errors, security gaps, or architectural drift.

Bloated CLAUDE.md

Stuffing every rule into CLAUDE.md defeats the purpose. Keep it focused on high-level rules; use docs/ and local CLAUDE.md for details.

Adaptive thinking & effort

On Opus 4.8, Opus 4.7, Opus 4.6, and Sonnet 4.6, adaptive thinking is the recommended mode. Instead of manually setting a thinking token budget, Claude dynamically decides when and how much to think based on task complexity. The /effort level is the primary lever that controls thinking depth:

EffortThinking Behavior
maxAlways thinks, no constraints on depth — deepest reasoning
xhighOpus 4.7 / Opus 4.8 — deeper than high, lighter than max; falls back to high on other models
highAlmost always thinks — deep reasoning on complex tasks
mediumModerate thinking — may skip for simple queries
lowMinimal thinking — skips for simple tasks, prioritizes speed

Toggle extended thinking with Option+T / Alt+T. Setting effort to low effectively minimizes thinking; use this for simple lookups or subagent tasks where speed matters most.

Dynamic Workflows — Parallel Multi-Agent Orchestration

▼

Dynamic workflows run tens to hundreds of parallel subagents in a single session — tackling problems too large for a single-pass solution. Claude decomposes the prompt, distributes subtasks across agents working simultaneously, verifies results through independent checking and adversarial refutation, and iterates until answers converge. "Work you'd normally plan in quarters now finishes in days."

"Create a workflow to migrate all API calls from v1 to v2"

# Or enable ultracode — Claude decides when to use workflows automatically

Subprocess Sandboxing

▼

Claude Code supports OS-level sandboxing that restricts what Bash subprocesses can read, write, and reach on the network — enforced by Seatbelt on macOS and bubblewrap on Linux / WSL2. Run /sandbox to enable it and choose a mode. Linux and WSL2 users must first install the required packages: sudo apt-get install bubblewrap socat (Ubuntu/Debian) or sudo dnf install bubblewrap socat (Fedora). Bash tool permission checking was also improved for zsh-specific syntax in shell conditionals, reducing false permission prompts for zsh-style conditional commands (v2.1.238). As of v2.1.246, Bash permission checks always require approval for malformed commands with a dangling && or || operator, closing a gap where a syntactically-broken compound command could otherwise skip the intended approval flow.

Sandbox modes

Auto-allowSandboxed bash commands run automatically without approval prompts. Commands that cannot be sandboxed (e.g. need access to non-allowed network hosts) fall back to the normal permission flow. rm targeting critical paths still prompts.
Regular permissionsAll bash commands go through the standard permission flow even when sandboxed — more control, more prompts. The sandbox still enforces the same filesystem and network boundaries.

Prompt Caching & KV Cache

▼

Claude maintains a key-value (KV) cache of computed attention states for the leading prefix of each conversation. When a new request shares the same prefix as a cached one, Claude skips recomputing that prefix — delivering faster responses at roughly 10% of the regular input-token cost for cached tokens.

The cache is prefix-based: content must appear at the beginning of the prompt to be cacheable. The first matching request in a window incurs a small cache-write overhead; every subsequent request within the TTL window is a cheap cache read.

What gets cached in a Claude Code session

  • System prompt injected by Claude Code at session start
  • CLAUDE.md files loaded from the project and user config
  • Large read-only documents attached at the top of the conversation
  • Accumulated conversation history prefix (up to the last assistant turn)

ENABLE_PROMPT_CACHING_1H=1Opt into 1-hour prompt cache TTL (API key, Bedrock, Vertex, Foundry). Improves hit rate for long or repeated sessions.
FORCE_PROMPT_CACHING_5M=1Force 5-minute TTL regardless of other settings.
promptCacheTtl (settings.json)Set the main conversation's prompt cache TTL to 1 hour (API key and cloud-provider users). Equivalent to ENABLE_PROMPT_CACHING_1H but configured in settings.json (v2.1.243).
subagentPromptCacheTtl (settings.json)Set subagent prompt cache TTL independently of the main conversation — subagents default to 5 minutes even when the main session uses a 1-hour TTL (v2.1.243).
experimental.cacheTtl (agent frontmatter)Set a prompt cache TTL ("5m" or "1h") for one specific agent, overriding the session-wide subagentPromptCacheTtl default when that setting isn't configured. Use when only a subset of your agents benefit from a longer TTL (v2.1.248).

TTLBest for
5 min (default)Short one-off sessions; acceptable when sessions rarely outlast 5 minutes; lowest storage overhead.
1 hourLong coding sessions, nightly CI pipelines, any workflow where Claude re-reads the same large codebase context repeatedly. Enable whenever a session is likely to outlast 5 minutes or runs on a schedule.

Persisting your TTL setting

For a global default across all projects, export from your shell profile (~/.zshrc or ~/.bashrc):

export ENABLE_PROMPT_CACHING_1H=1
Structuring Prompts for Maximum Cache Hits
  • Stable content first — system prompt, CLAUDE.md, and large reference docs must form a leading prefix; dynamic content (task description, user message) goes last.
  • Multi-user / CI deployments — use --exclude-dynamic-system-prompt-sections to strip per-user dynamic injections so the shared system-prompt prefix is cacheable across all users.
  • Observe cache activity — OTEL events include cacheRead and cacheCreation token breakdowns under claude_code.token.usage so you can confirm cache hits in your monitoring.

Hooks — Automation & Guardrails

Automate workflows, enforce policies, and extend Claude Code with event-driven hooks. Models forget. Hooks don't.

Hooks are user-defined shell commands, HTTP endpoints, LLM prompts, or agents that execute automatically at specific points in Claude Code's lifecycle. They fire deterministically — unlike instructions in CLAUDE.md that Claude may or may not follow, hooks always execute when their event triggers.

Hyphenated identifiers (e.g. code-reviewer, mcp__brave-search) contain - so they are treated as regex and exact-match the literal name. To match all tools from a hyphenated MCP server, append __.*: use "mcp__brave-search__.*" instead of "mcp__brave-search" (v2.1.195).

Conditional if field — narrows which tool calls trigger a hook:

  • "Bash(git *)" — only git commands
  • "Bash(rm *)" — only rm commands
  • "Edit(*.ts)" — only TypeScript edits
  • "Write(*.md)" — only Markdown writes

Path-scoping (v2.1.214): A single-segment pattern like "Edit(src/**)" in an if: condition matches only <cwd>/src/ — not a src/ directory nested deeper in the tree. Write "Edit(**/src/**)" to match at any depth. Note: deny/ask permission rules keep their any-depth behavior — this scoping applies only to hook if: conditions.

Command-substitution false-fires fixed (v2.1.243): Earlier versions could false-fire an if condition like "Bash(cat *)" on an unrelated command if it contained $() or backtick command substitution followed by more arguments. This is fixed as of v2.1.243 — such conditions now match only the intended command.

Exit Codes & Decision Control

▼

Exit codes determine whether a hook blocks execution or just logs a warning. Getting this right is critical for policy enforcement.

Exit CodeBehavior
0Success — stdout parsed for JSON output. Most events: written to debug log. Exceptions: UserPromptSubmit and SessionStart show stdout as context.
2Blocking error — blocks tool call, rejects prompt, prevents stop, or blocks compaction (depending on event). Stderr is fed back as the error message.
Any otherNon-blocking error — stderr shown as warning in transcript. Execution continues normally.
Exit 2 Is the Only Blocking Code

Exit 1 is non-blocking — it logs an error but doesn't stop anything. You must use exit 2 to enforce policy. This is the most common mistake when writing hooks.

PreToolUse permission decisions — control what happens to the tool call:

DecisionEffect
allowSkip permission prompt, execute immediately
denyBlock the tool call entirely
askPrompt the user to confirm
deferPause for later (non-interactive -p mode only)

When multiple hooks fire, precedence is: deny > defer > ask > allow.

PreCompact blocking — prevent context compaction from running:

MethodEffect
Exit with code 2Block compaction; stderr shown as reason
Return {"decision":"block"}Block compaction via JSON decision output

PostToolUse output replacement — replace the tool's output before Claude sees it:

{
  "hookSpecificOutput": {
    "updatedToolOutput": "Sanitized or transformed output here"
  }
}

Return this JSON from a PostToolUse hook (exit 0) to substitute the tool result Claude receives. Works for all tools — use it to redact sensitive output, normalize formats, or inject additional context.

PostToolUse continueOnBlock — soft block: feed the rejection reason back to Claude instead of ending the turn:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/check-output.sh",
            "continueOnBlock": true
          }
        ]
      }
    ]
  }
}

When "continueOnBlock": true is set, a hook that exits 2 (block) feeds its rejection reason back to Claude as a tool result and the turn continues — Claude can retry or adjust. Without this option, a block ends the turn immediately. Use continueOnBlock for "soft guard" patterns where you want Claude to self-correct rather than halt.

Hook terminalSequence — emit terminal escape sequences (desktop notifications, window title, bell) from any hook:

{
  "terminalSequence": ""
}

Return a JSON object with a terminalSequence key from any hook (exit 0). Claude Code writes the value directly to the terminal — even when there is no controlling TTY. Common sequences: "" rings the terminal bell; "]2;Task done" sets the window title. Use this to provide ambient feedback without wrapping Claude Code in a shell script or requiring a controlling terminal.

Continuous Evals in CI

▼

Hooks and one-off checks catch known failure modes, but they don't tell you whether a change to CLAUDE.md, a skill, or a hook made the agent worse at real work. A continuous eval suite closes that gap: a small, growing library of real tasks — each captured as a prompt plus acceptance checks — that runs non-interactively in CI and gates any change to your agent-steering configuration before it merges.

Most teams start with 20–50 cases pulled from actual recent work — a bug fix, a refactor, a feature slice, an edge case someone got wrong. Each case is stored as a prompt (the task phrased the way a user would ask it) plus 2–4 acceptance checks — commands or assertions that must all pass for the run to count as a success: tests pass, lint is clean, behavior outside the target area is unchanged, and any team policy (no git push --force, no editing .env, etc.) was respected.

The suite runs two ways:

  • On a schedule — nightly or via cron, to catch drift from model updates, dependency bumps, or unrelated config edits.
  • As a merge gate — on every pull request that touches CLAUDE.md, a skill, or a hook, the same way a unit test suite gates application code. The PR can't merge until the eval suite passes.
Every incident becomes a permanent test

The suite's real power is compounding growth: every production incident becomes a permanent eval case. When an agent does something wrong in the wild, don't just fix the immediate issue — write the prompt and acceptance check that would have caught it, and add it to the suite. Over months this becomes a living regression test of every mistake the team has already paid for once, so the same mistake can't silently reappear after the next config change.

Example eval case:

id: eval-023
source: incident-2026-04-11   # promoted from a real production bug
prompt: >
  Add input validation to the POST /api/users endpoint so a request
  missing the "email" field returns a 400 with a clear error message,
  instead of a 500.
acceptance:
  - name: tests pass
    run: npm test -- users.routes.test.js
  - name: lint clean
    run: npm run lint -- src/api/users.js
  - name: change is scoped
    run: '[ "$(git diff --name-only | grep -vc "^src/api/users.js")" = "0" ]'

Cloud Integrations

Connect Claude Code to external services via HTTP hooks, and deploy Claude as a fully managed cloud agent for long-running autonomous work — no agent loop required.

HTTP Hooks — Webhook Integrations

▼

HTTP hooks ("type": "http") POST Claude Code lifecycle events as JSON to any HTTP endpoint. Unlike command hooks, the receiving server doesn't need to be co-located with the developer — enabling team-wide shared audit services, remote approval gateways, and webhook-based integrations with Slack, PagerDuty, GitHub Actions, and custom dashboards.

HTTP hook schema:

{
  "type": "http",
  "url": "https://your-service.example.com/hooks/tool-use",
  "headers": {
    "Authorization": "Bearer $HOOK_TOKEN",
    "X-Team": "platform-eng"
  },
  "allowedEnvVars": ["HOOK_TOKEN"],
  "timeout": 10
}

Header values support $VAR or ${VAR} interpolation. Only env vars listed in allowedEnvVars are expanded — all others remain empty strings.

Recipe 1 — Team audit log service (PostToolUse):

Every tool call across your team's Claude Code sessions is POSTed to a shared logging endpoint. The body is the standard PostToolUse JSON (session_id, tool_name, tool_input, tool_output). Index this into Elasticsearch, Datadog, or any observability stack.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash|Edit|Write",
        "hooks": [
          {
            "type": "http",
            "url": "https://audit.internal/api/claude-events",
            "headers": { "Authorization": "Bearer $AUDIT_TOKEN" },
            "allowedEnvVars": ["AUDIT_TOKEN"]
          }
        ]
      }
    ]
  }
}

Recipe 2 — Slack notification on task completion (Stop):

Post a message to your team's Slack channel whenever Claude finishes a turn. The Stop event fires each time Claude stops responding — pair with a Slack incoming webhook URL for real-time task completion alerts.

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "http",
            "url": "$SLACK_WEBHOOK_URL",
            "headers": { "Content-Type": "application/json" },
            "allowedEnvVars": ["SLACK_WEBHOOK_URL"]
          }
        ]
      }
    ]
  }
}

Recipe 3 — External approval gateway (PreToolUse):

Before allowing destructive Bash commands in a regulated environment, POST to an approval service. The service evaluates the command against policy and returns a JSON decision body. Blocking requires a JSON response body — an HTTP 4xx status alone won't stop the action.

// Hook config
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "http",
            "url": "https://policy.internal/approve",
            "headers": { "Authorization": "Bearer $POLICY_TOKEN" },
            "allowedEnvVars": ["POLICY_TOKEN"],
            "timeout": 15
          }
        ]
      }
    ]
  }
}

// Your server returns this JSON to block:
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Command violates SOC2 policy: rm -rf on /data"
  }
}

// Or this JSON to allow:
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow"
  }
}
HTTP Hooks — What to Watch Out For
  • Blocking requires JSON body, not HTTP status. Return a 2xx response with the appropriate hookSpecificOutput JSON. A 403 or 500 causes a hook error — execution continues, it does not block.
  • Always list env vars in allowedEnvVars. Any $VAR in headers not in this list expands to an empty string — no error, just silent auth failures.
  • Set timeout explicitly for fast gates. Default is 10 minutes. An approval gateway that hangs will block Claude for 10 minutes if you don't specify a lower timeout (e.g., "timeout": 10 seconds).
  • Non-2xx responses cause hook errors — execution proceeds. If your server returns a 500, Claude Code logs a hook error but does not block the action. Design your server to return 2xx with a deny body, not an HTTP error code.

Closing the Loop: From Incident to Intent

The FSAD workflow (intent → spec → plan → execution → review) is a forward pipeline. A production breach should re-enter that same pipeline automatically, not wait for a human to file a ticket. This is the "Maintain" stage: a monitoring agent watches a rolling-baseline production metric and escalates through statistical control bands.

Control Bands: 1σ / 2σ / 3σ

▼

Pick a rolling-baseline metric that reflects delivery or system health — CI test failure rate, post-deploy 5xx rate, or PR cycle time all work. Compute a rolling mean and standard deviation over a trailing window, then respond to breaches in tiers instead of a single fixed threshold:

TierTriggerResponse
1σMetric drifts one standard deviation from baselineLog only — no agent action, just a recorded data point
2σMetric crosses two standard deviationsClaude runs a read-only diagnosis — inspects logs, recent deploys, and traces to form a hypothesis, no changes made
3σMetric crosses three standard deviationsClaude proposes a fix — opens a PR, or executes a pre-approved runbook, gated by the same human-review checkpoint as any other change

A rolling baseline (not a fixed threshold) matters because it adapts to normal seasonal or growth-driven drift — you're watching for anomalies relative to recent behavior, not an arbitrary static number that goes stale.

Closing the Loop: Breach → Intent

▼

The output of a 2σ or 3σ diagnosis is not a Slack message — it's a new intent.md-style markdown artifact, written in the same format Phase 1 of the workflow produces. That artifact captures what broke, the suspected cause, and supporting evidence (logs, traces, the suspect deploy), then hands off to a human for triage exactly like any other intent.

This is what makes the loop closed rather than linear: a production incident doesn't require a human to notice, reproduce, and write up the problem before planning can start. The agent has already done that framing work by the time a human looks at it — the incident re-enters the pipeline at Phase 1 (Intent & Discovery) as a pre-drafted problem statement, then flows through spec, plan, execution, and review like any other change.

# bands.yaml — control-band config for a monitoring agent
metric: post_deploy_5xx_rate
baseline_window: 14d
bands:
  - sigma: 1
    action: log
  - sigma: 2
    action: diagnose        # read-only: Claude inspects logs/traces, no changes
    output: intent.md        # drafted, not filed — awaits human triage
  - sigma: 3
    action: propose_fix      # Claude opens a PR or runs a pre-approved runbook
    require_human_review: true
This Is Phase 1 of the Workflow, Not a New Pipeline

The breach-generated intent.md is deliberately shaped like any other Workflow Phase 1 artifact. No separate incident-response track exists — production monitoring feeds the same intent → spec → plan → execution → review loop, so "Maintain" is the phase that turns the pipeline into a closed loop instead of a one-way street.
