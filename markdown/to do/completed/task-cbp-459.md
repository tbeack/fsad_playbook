# CBP-459 — Implement `playbook-updater`'s Strategy 2 refactor (serialize fan-out; move the verification gate + release steps to the root skill session)

## Source
Follow-on implementation task for `CBP-457` (`markdown/to do/completed/task-cbp-457.md`), which researched `playbook-updater`'s repeated coordination stalls (5 incidents, 2026-08-05 through 2026-08-26) and recommended **Strategy 2, with Phase 5.5 and everything it gates hardened by Strategy 1's root-dispatch mechanism** — see that task's Recommendation section for the full reasoning and tradeoffs. This task turns that recommendation into two concrete file edits. The repo owner approved proceeding with Strategy 2 and requested this task and plan directly (no separate `tb:add-task` round-trip).

## Summary
Rewrite `~/.claude/agents/playbook-updater.md` so Phases 3 and 5 run as plain serial loops in the agent's own context — no `Agent`-tool fan-out, no named sub-agents, no `ListAgents`/`SendMessage` polling. Remove Phase 5.5, Phase 6, and Phase 7 from that file entirely. Move them into `~/.claude/skills/cbp-update/SKILL.md`, which becomes a real orchestrator: it spawns `playbook-updater` for Phases 0–5 only, receives the diff back as that spawn's normal completion (this is the one Agent-call boundary in the whole design, and it already works reliably — a root session receiving its own direct child's completion is this project's proven, unbroken case), dispatches a single unnamed verifier for Phase 5.5, and — gated on `PASS` — performs Phase 6 (version bump, CHANGELOG, README, dist build) and Phase 7 (branch, commit, PR, merge) itself. Delete `~/.claude/agents/playbook-updater-proposer.md`, which becomes unused once Phase 5 no longer proposes edits through a separate read-only role. Both edited/deleted files live in `~/.claude/`, outside this git repo — these changes are not part of any commit to `fsad_playbook` and need no `dist/` rebuild themselves; only a subsequent live `/cbp-update` run (this task's acceptance test) touches the repo.

## Assessment

**Current state of `~/.claude/agents/playbook-updater.md` (338 lines):**
- Phase 3 (`:125-149`) fans out the ~15 anchor-group sweep to 3–4 named sub-agents (`sweep-batch-a/b/...`), then actively polls `ListAgents`/`SendMessage` for results, with a bounded wait and `STALLED` fallback.
- Phase 5 (`:171-199`) does the same for task execution, dispatching to `subagent_type: "playbook-updater-proposer"` in named batches, then serializes only the final write-back to `fsad-playbook.html`.
- Phase 5.5 (`:200-219`) spawns a single named `diff-verifier`, polls for its `PASS`/`FAIL` verdict, and gates everything after it.
- Phase 6 (`:221-234`) and Phase 7 (`:236-301`) run version-bump/changelog/PR/merge, still inside `playbook-updater` itself.
- Guardrails (`:318-335`) and Success Criteria (`:303-316`) both describe and depend on the named-agent/active-polling design throughout — these need to shrink alongside the phases they were written to support, not just the phase bodies.
- `~/.claude/agents/playbook-updater-proposer.md` exists as a dedicated read-only (`Read`/`Grep`/`Glob` only) role whose entire purpose is "propose an edit, can't write it yourself" (`playbook-updater.md:178`) — a guarantee Strategy 2 replaces with "there's no concurrent dispatch to guard against in the first place," per `CBP-457`'s Strategy 2 tradeoffs.

**Current state of `~/.claude/skills/cbp-update/SKILL.md` (39 lines):** a thin, one-shot delegate-and-wait skill. Its Instructions section (`:11-25`) spawns `playbook-updater` once, unnamed, covering the *entire* Phase 0–7 workflow, and just waits for that single completion. Its Liveness section (`:27-31`) already anticipates an unattended/scheduled caller with no one actively waiting — that section's reasoning (root-vs-non-root awareness of the failure mode) stays valid under the new design and does not need rewriting, only re-scoping to "no commit / no terminal status within 20 minutes of dispatch," which already covers the new shape.

**What does not need to change:** Phase 0–2 and Phase 4/4a's actual logic (fetch releases, gather details, create tasks) is orthogonal to the coordination-primitive problem — none of it dispatches sub-agents. It moves into the new serial Phase 3/5 structure unchanged.

## Plan

1. **Rewrite Phase 3** (`playbook-updater.md`) as a plain loop: for each of the ~15 anchor groups (still listed by name, unchanged), read the relevant HTML slice and the Phase 2 change list, and produce the same structured finding (`{change, anchorGroup, verdict, reason, targetLineRange}`) directly — no `Agent` call, no `name:`, no polling. Delete the "Fan out... actively poll" instructions, the "Why a name" rationale block, and the bounded-wait/`STALLED`-for-Phase-3 text; replace with a short "walk every anchor group in order; do not skip any" instruction.

2. **Rewrite Phase 5** the same way: loop over tasks created in Phase 4, read each task's plan plus the relevant `fsad-playbook.html` section, and edit the file directly and immediately per task — no `playbook-updater-proposer` dispatch, no batching, no named sub-agents. The "serialize the write-back" note becomes moot (there's only ever one writer now) and can be deleted along with it.

3. **Remove Phase 5.5, Phase 6, and Phase 7 from `playbook-updater.md` entirely.** Phase 5's last step becomes: end the turn with a final message reporting (a) whether new versions were found, (b) the full list of CBP task IDs created and executed, (c) the path to the daily report, (d) `git diff fsad-playbook.html` in full, and (e) any `## Deferred` / `## Execution Gaps` entries logged along the way. This final message is what the root `cbp-update` session receives as `playbook-updater`'s normal completion — the one Agent-call boundary this design still has, and the one this project has never observed to fail (a root session receiving its direct child's own completion).

4. **Trim Guardrails and Success Criteria** (`playbook-updater.md:303-335`) to match: delete every bullet whose subject is named-agent dispatch, active polling, `STALLED` status, or the `run_in_background`/`Workflow` history (that history now belongs in `CBP-457`'s diagnostics, not in the live agent's operating instructions — a currently-non-functional design shouldn't be documented as the live behavior). Keep the sync-to-main, no-self-respawn, spawn-depth, never-commit-to-main-directly, and no-secrets guardrails — none of those are about coordination and all still apply. Success Criteria's Phase 5.5/6/7 cross-checks move to `SKILL.md` (step 8 below) since those phases now live there.

5. **Delete `~/.claude/agents/playbook-updater-proposer.md`.** Confirm nothing else references `subagent_type: "playbook-updater-proposer"` before removing it (`grep -rl playbook-updater-proposer ~/.claude/`).

6. **Rewrite `cbp-update/SKILL.md`'s Instructions section** to spawn `playbook-updater` for Phases 0–5 only (update the `prompt:` string to list only those phases, dropping the "(5.5) independent verification gate, (6)... (7)..." clauses it currently names). Wait for its completion exactly as today (`:23`'s "wait for it to return" guidance is already correct and stays).

7. **Add a new "Phase 5.5 — Verification" section to `SKILL.md`**, run by the (root) session executing the skill: dispatch **one unnamed** `Agent` call (`general-purpose`, no `name:` — this is the normal fire-and-forget convention, safe here because the dispatcher is root) carrying the diff, source changelog entries, and task list from `playbook-updater`'s completion message; instruct it as a refuter with the same falsification checklist `playbook-updater.md:209-213` already specifies (unclosed tags, misrepresented content, unsupported claimed changes, broken table/collapsible structure), ending with a `VERDICT: PASS`/`VERDICT: FAIL` line. Since this is a single, unnamed, root-dispatched call, no polling is needed — its result returns as the normal tool/completion result of that one call.

8. **Add "Phase 6 — Version & Changelog" and "Phase 7 — Branch, Commit & PR" sections to `SKILL.md`**, gated on step 7's verdict: on `FAIL`, stop and report the failure (and the verifier's reasoning) to the user — no version bump, no branch, no PR. On `PASS`, port `playbook-updater.md`'s current Phase 6 (`:221-234`) and Phase 7 (`:236-301`) content into `SKILL.md` essentially verbatim (version-triple bump, CHANGELOG/README updates, `dist/` rebuild, branch naming, `completed/` task-file moves, commit, push, PR body, auto-merge) — these steps don't depend on which session executes them, only on having `Write`/`Edit`/`Bash`/`gh` access, which the root session invoking the skill already has. Carry forward the Success Criteria cross-checks (`playbook-updater.md:303-316`) into this same section, since Phase 4 (task list) and Phase 5.5 (verification) both now live across the Phase 0-5/root-session boundary rather than in one file.

9. **Smoke-test the new root-dispatched Phase 5.5 call in isolation before relying on it end-to-end**, per `CBP-457`'s carried-forward caveat: a root session's *single* (non-fanned) verifier dispatch has not previously been exercised in this project, even though root-dispatched fan-out (`code-review-team`, etc.) is well-proven. Do this as a standalone check — spawn one unnamed verifier against a trivial synthetic diff and confirm the verdict returns normally — before the first real `/cbp-update` run under the new design.

10. **Run a full live `/cbp-update` invocation** as the end-to-end acceptance test (Acceptance Criteria below) — this is the first real exercise of the complete new design and is what actually validates it, not a reading of the rewritten files alone.

11. **Update `README.md` and this task's own `## Summary`-sourced changelog entry** if the live run in step 10 produces a version bump — same as any other CBP task, per this repo's `CLAUDE.md` version-bump checklist. (This is about the *next* `/cbp-update` run's own version bump, not a version bump for CBP-459 itself — CBP-459 only edits files outside this repo.)
