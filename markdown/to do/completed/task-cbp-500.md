## Assessment

**Source content (paraphrased, not copied) — full narrative breakdown to adapt:**

The source thread opens with a familiar failure story: a team sees an agent misbehave, so they tune the prompt, then swap in a bigger model, then widen the context window — and the agent still forgets decisions, still reaches for the wrong tool, still skips verification, still loops. The thread's diagnosis is that the fix targets the wrong layer: intelligence isn't the bottleneck, the *environment around* the model is. It names that environment "the harness" and cites Dario Amodei describing this exact shift while explaining how Claude Code emerged (model as reasoning engine; harness decides what it can see, touch, remember, and when it must stop), plus OpenAI's own account of building an agent-first codebase with Codex — their early slowdown came from an underspecified environment, not a weak model, and the fix was to make missing capabilities both legible and enforceable rather than telling the agent to "try harder." Both citations back the same closing point item 10 below: when an agent fails repeatedly, stop editing adjectives in the prompt and inspect the system around the model. This is the section's opening beat and should frame everything after it.

1. **Model vs. harness thesis.** The model is the reasoning engine — it can propose the next action but cannot construct a reliable operating environment for itself. The harness is that environment: it selects context, exposes tools, stores state, enforces permissions, checks results, records traces, and recovers from failure. The same weights, dropped into a chat box, just answer questions; dropped into a repo with terminal access, tests, browser tools, project memory, isolated worktrees, and a review loop, they can ship software. The weights didn't change — the harness did. A simple two-box diagram (MODEL: reasons and proposes actions ↔ HARNESS: selects context / exposes tools / stores state / enforces permissions / checks results / records traces / recovers from failure) is the source's own framing device for this and is worth adapting as this section's opening diagram.

2. **The seven jobs of a production harness** — each is a distinct sub-topic with its own worked example in the source, and each should get its own collapsible/subsection rather than being flattened into one list:
   - **(a) Turn the request into a contract.** Before the agent acts, convert the request into a bounded object with a goal, inputs, expected output, explicit constraints, and done-when conditions — e.g. `{goal, inputs, output, constraints, done_when}`. Without this, an agent can quietly complete a different job than the one asked and still declare success; the contract is what prevents silent scope redefinition.
   - **(b) Give the agent a map, not a manual.** Agents need project knowledge but not every document stuffed into every context window. A small root guide (the source uses `AGENTS.md`; this playbook's equivalent is `CLAUDE.md`) should point outward to an architecture map, testing map, product rules, security rules, and task-specific guides, loaded only when the current task needs them. A map preserves context; a giant manual consumes it.
   - **(c) Expose the right tools inside the right environment.** Tool access isn't a list of buttons, it's an interface between the model and the real world — every tool needs a clear purpose, predictable output, an explicit failure state, and a permission boundary (e.g. reading files allowed by default, running tests allowed inside a sandbox, writing files allowed inside the workspace, network access scoped by task, deploys and deletes requiring approval). Good tools reduce ambiguity before the model has a chance to reason badly; bad tools force it to guess what happened.
   - **(d) Externalize memory into durable state.** The conversation itself is not the system of record. Decisions, artifacts, failures, and open risks should live outside the context window in structured state (task id, current step, artifacts produced, decisions made, failures hit, pending approvals) so the next session inherits the actual state of the work rather than a lossy retelling of the conversation — this is what lets an agent survive context resets, crashes, and handoffs.
   - **(e) Add sensors before adding autonomy.** An agent can't correct what it can't observe. Tests, linters, screenshots, logs, metrics, and schema validators turn vague "looks good" quality judgments into evidence, mapped by artifact type (code → tests/type checks/lint; UI → render + screenshot + visual inspection; research → source check + contradiction check; data → schema/range/freshness checks). The model produces an artifact; the environment produces evidence about it; the harness decides whether that evidence is sufficient to continue.
   - **(f) Enforce permissions outside the model.** The model can recommend an action, but the harness must authorize it — a strict `MODEL SUGGESTS → POLICY CHECKS → TOOL EXECUTES` pipeline. This separation matters most for actions that are expensive, irreversible, or that touch another person; the same probabilistic system should not be the one that invents the plan, approves the risk, *and* executes the side effect.
   - **(g) Record traces and recover locally.** Every run should leave a readable trail: the request, the context selected, tool calls made, state changes, verification results, retries, cost, the final artifact, and a rollback point. Without traces, failure is a mystery you can't learn from; with traces, failure becomes input for the next harness improvement.

3. **Instructions should become infrastructure.** Prose rules eventually get read once and then ignored. The stronger pattern encodes an important rule twice — once as guidance a person or agent can understand (e.g. "UI code may not query the database directly"), and once as a mechanical check the agent literally cannot bypass (e.g. a lint rule that fails when UI code imports the repository layer). The guide explains *why*; the check enforces the boundary. This converts a one-off past failure into a permanent system improvement — the next agent doesn't need to remember the incident because the harness remembers for it.

4. **The retry loop belongs to the harness, not the model.** "Keep trying until it works" is not a control system. A useful loop needs evidence, bounded retries, a budget, and an explicit escalation path — the source's example is a numbered `for` loop that builds, verifies against evidence, and on 3 failed attempts falls through to `requestHumanReview(state)` rather than looping forever. The model decides *how* to repair a local gap; the harness decides *whether* another attempt is even allowed. The source notes Anthropic reached a similar conclusion in its own work on long-running agents: structured artifacts preserve continuity across sessions, and a separate evaluator gives the builder concrete feedback instead of letting it grade its own homework.

5. **Failure should upgrade the system, not just the current output.** Most people patch the one broken run; harness engineers repair the *class* of failure by mapping each failure type to a durable system change — missing context → add a map/retrieval rule, wrong tool → improve its description or routing, bad output → add a validator or stronger contract, a repeated loop → add a retry cap and escalation, an unsafe action → add a permission gate, a lost decision → store it in durable state, an unknown failure → add tracing and evidence capture in the first place. The immediate patch fixes one run; the harness change improves every run after it — that compounding effect is the actual payoff of harness engineering.

6. **Separate the brain, the hands, and the history.** A reliable agent is easier to reason about, debug, and evolve when three components stay distinct: the BRAIN (the model that reasons), the HANDS (the sandbox and tools that act), and the HISTORY (the append-only record of what happened). If the sandbox dies, history survives; if the model changes, tools and policy remain inspectable; if a task resumes, a new session can reconstruct state purely from artifacts and traces. The source cites Anthropic's Managed Agents architecture as making this separation explicit via session/harness/sandbox — the point isn't the vendor, it's the architecture: the reasoning engine should not also be the filesystem, the permission system, the memory database, and the audit log all at once.

7. **Give every run a change receipt.** Don't keep only the final output — keep a compact structured receipt of how it was produced: context sources used, policy version, model route, tools used, test pass/fail counts, human corrections, retries, cost, the accepted artifact, and a rollback point. This makes model upgrades comparable, regressions attributable to a specific cause, audits possible, and prevents a good-looking final answer from hiding a broken process underneath it.

8. **Start with the smallest harness that closes the loop.** Harness engineering doesn't mean building a platform before the first task — start with the smallest system that can observe, verify, and recover, then earn complexity as task risk grows. The source's 4-level maturity ladder: **Level 0** — prompt + model; **Level 1** — project guide + tools; **Level 2** — structured state + tests + a bounded loop; **Level 3** — permissions + traces + recovery + human gates. A short low-risk task may need only one prompt and one human review; a six-hour coding run that edits files, hits the network, and opens a PR needs a real harness. Rule of thumb: the harness should be smaller than the failure surface it controls, not larger.

9. **The harness engineering checklist** — a ~12-item self-assessment readers can run before trusting an agent with real work: is success defined before execution begins; can the agent find the right project knowledge without loading everything; does every tool have a clear contract and failure state; is execution isolated from production systems; are important decisions stored outside the conversation; does every risky transition have evidence; are irreversible actions protected by approval; does every loop have a retry cap and budget; can the run resume after interruption; can you explain every tool call and state change; does failure update a guide, test, tool, or policy; can the final artifact be rolled back. The source's punchline: if several answers are "no," a stronger model won't make the system reliable — it will only make the failure more expensive when it happens.

10. **The closing taxonomy — "the real shift."** Prompt engineering tells the model what to do. Context engineering decides what the model sees. Harness engineering builds the world in which the model acts. The source extends this into a five-row table worth reproducing directly: `PROMPT → instruction`, `CONTEXT → working view`, `HARNESS → operating system`, `LOOP → local improvement`, `GRAPH → coordination`. Its final argument is that the model may change next month, but the tools, tests, state, policies, and traces around it can keep improving regardless — durable advantage is moving out of the prompt and into the system around it. The best builders won't only ask which model is smartest; they'll ask which environment makes that intelligence reliable. That's harness engineering — a strong closing line for the section.

This maps naturally onto FSAD's own vocabulary already used elsewhere in the playbook (pods, skills, hooks, permissions, verification loops, sec-review-team's evidence-gated pipeline) — the new section should draw those parallels explicitly rather than reading as an unrelated import. Concrete pairing candidates for a light-touch "in this repo" callout per subsection: item 2(e)/9 ↔ this repo's AC-verification pattern (evidence gates a task as done); item 2(g)/7 ↔ `tb:session-log`/change-receipt-style run records; item 3 ↔ hooks that mechanically enforce a `CLAUDE.md` rule; item 6 ↔ pods separating a model's role from the sandboxed tools it's given; item 8 ↔ matching pod/skill complexity to task risk rather than always reaching for the heaviest multi-agent setup.
