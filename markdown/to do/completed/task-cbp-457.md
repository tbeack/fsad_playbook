# CBP-457 — Refactor the `playbook-updater` agent's multi-agent coordination design

## Source
Live incident during the 2026-08-26 `/cbp-update` run (session `fsad-playbook-55`). Phase 3's HTML-impact sweep was dispatched to three named sub-agents (`sweep-batch-a/b/c`) per the design shipped after the 2026-08-24/25 stall (`markdown/updates/agent-stall-2026-08-25-diagnostic.md`). The orchestrator went idle immediately after dispatch, reporting that it would resume "as soon as [the sub-agents'] findings arrive" via `SendMessage` — i.e. it did not, and structurally could not, actively poll `ListAgents` as its own instructions require. The run sat stalled for ~24 minutes until a human intervened; all three sub-agents and the orchestrator were then manually killed via `TaskStop`. Investigation in the same session confirmed why: `ListAgents` and `notify_when_idle` are both scoped to root/top-level sessions only and are unavailable to `playbook-updater`, which is by design always a spawned, non-root agent. This is the same class of failure documented in two prior incidents (CBP-365, CBP-406/407) and the 2026-08-24/25 diagnostic — each fix has patched around the previous one's false assumption about which coordination primitive is available to a non-root agent, without addressing the structural mismatch itself. **Corrected:** the earlier 2026-08-05 incident (CBP-340/342, also in the incident history below for completeness) is a *different* root cause — two stale, diverged copies of the agent definition file on disk — not a coordination-primitive-availability failure, and is not part of this pattern.

## Summary
The `playbook-updater` agent's design has become progressively more complex — named sub-agents, active polling, bounded waits, `STALLED` status reporting, self-checks for duplicate definitions and self-respawn — almost entirely in service of working around the same unresolved problem: **no multi-agent coordination primitive tried so far (`Agent`-call completion notifications, the `Workflow` tool, `ListAgents`, `notify_when_idle`) is actually available to a non-root spawned agent instance**, which `playbook-updater` always is. This task researches the failure history, confirms the root cause with fresh evidence, and develops 3 distinct refactor strategies with tradeoffs and a recommendation. **This is a planning task — no changes to `~/.claude/agents/playbook-updater.md` or `~/.claude/skills/cbp-update/SKILL.md` are made here.**

### The actual pattern

Every incident from 2026-08-07 onward is a variation on the same structural problem, not five unrelated bugs:

1. **2026-08-07:** assumed a synchronous `Agent` mode existed (`run_in_background: false`). It didn't.
2. **2026-08-24/25, Attempt 1 (abandoned):** migrated to the `Workflow` tool, which genuinely does await spawned agents synchronously. Live-tested and found **not registered as a tool at all for any spawned agent instance** — root/interactive sessions only.
3. **2026-08-24/25, Attempt 2 (shipped):** fell back to named sub-agents + active `ListAgents` polling, reasoning that `ListAgents` is "a synchronous status check, unaffected by [the notification-delivery problem]." This diagnosis under-scoped the actual constraint: it isn't specific to notification delivery, it's that **the entire family of cross-session/cross-agent introspection and messaging tools (`Agent`-notification delivery, `Workflow`, `ListAgents`, `notify_when_idle`) is root-only**, and `playbook-updater` is never root.
4. **2026-08-26 (today):** Attempt 2 failed for exactly the reason Attempt 1 did — the tool it depends on doesn't exist in its execution context.

The `agent-stall-2026-08-25-diagnostic.md` write-up even flagged this as a known residual risk ("whether `SendMessage`'s reply-to-a-message path reliably routes back to a non-root sender... has not been independently verified") but shipped anyway, and the specific gap that broke this time (`ListAgents` itself, not just the `SendMessage` reply path) wasn't the one flagged.

**Root cause, stated precisely:** `playbook-updater`'s Phase 3/5/5.5 design requires the *dispatching* agent to actively observe or be notified about its *own dispatched children's* completion. Every mechanism tried for this (implicit completion notification, `Workflow`, `ListAgents`, `notify_when_idle`) is confirmed unavailable to a non-root dispatcher. `playbook-updater` is non-root by construction — it is always spawned via the `Agent` tool by the `cbp-update` skill or the scheduled routine. This is not a wording or instruction-following problem; it is an availability mismatch between what the design needs and what the agent's execution context can provide, and it has now been "fixed" twice by substituting one unavailable primitive for another.

## Plan — Research findings and 3 refactor strategies

*(This section, and this task as a whole, makes no edits to `~/.claude/agents/playbook-updater.md` or `~/.claude/skills/cbp-update/SKILL.md` — see AC-05. All 3 strategies below are proposals for a follow-on implementation task to act on, not changes made here.)*

### Strategy 1 — Make the orchestrator root; eliminate the scoping mismatch at its source

**What changes:** Stop spawning `playbook-updater` as a `subagent_type` via the `Agent` tool at all. Move the Phase 0–7 procedure into the `cbp-update` skill itself, executed inline by whatever session invokes it (an interactive session, or the scheduled `RemoteTrigger` routine's own top-level session — both are root in the Agent-tool-scoping sense; "root" here means "not spawned via the `Agent` tool," not "has a human watching"). The invoking session becomes the orchestrator directly.

**What it fixes:** Root sessions have confirmed, working access to `ListAgents`, `notify_when_idle`, and reliable completion-notification delivery for `Agent` calls they make. Phase 3/5/5.5 fan-out can then use plain **unnamed** `Agent` calls — this project's normal fire-and-forget convention — because the dispatcher really is root and really does receive completion notifications reliably. The entire named-agent + active-polling + bounded-wait + `STALLED`-status apparatus becomes unnecessary and can be deleted.

**Tradeoffs:**
- Loses the clean "one-line delegation" shape of the current `cbp-update` skill; the skill becomes a large, stateful inline procedure.
- The invoking session needs `Agent`, `Bash`, `WebFetch`, `Write`, `Edit` etc. directly rather than through a dedicated agent's `allowed-tools` allowlist — loses that scoping/audit boundary.
- **Added — auto-merge identity gap.** `/cbp-update` is documented in `ONBOARDING.md` as a command distributed to and run by teammates generally (not just this repo's owner), roughly 4x/month. Under Strategy 1, "whatever session invokes it" becomes the orchestrator directly, so Phase 7's auto-merge-without-review behavior — an accepted norm for the repo owner's own workflow per this repo's `CLAUDE.md` — would execute under *that teammate's own* git/gh identity when they run the command. Nothing in this plan states whether that's intended, permitted, or should be scoped differently (e.g. restricted to a designated identity) before Strategy 1 ships.
- **Corrected (was previously understated):** `cbp-update`'s own Liveness section describes an unattended `RemoteTrigger`-dispatched routine, but **no such routine currently exists on disk.** The only scheduled-invocation artifact anywhere in this repo, `scripts/com.fsad.playbook-updater.plist`, is a stale, non-functional `launchd` job pointing at an unrelated stale copy of the project (`~/Desktop/AI/fsad_playbook`) whose target script doesn't exist. So "root-ness of the scheduled session" isn't a claim that can be tested against anything real today — it must be confirmed the first time a real `RemoteTrigger` routine is actually created, before Strategy 1 (or the Recommendation's Phase 5.5 hybrid below) is relied on for that path. This task neither builds nor assumes that routine exists.

**Implementation sketch:** Delete `~/.claude/agents/playbook-updater.md`'s existence as a spawnable agent; fold Phases 0–7 into `~/.claude/skills/cbp-update/SKILL.md` as the skill's own executed instructions (or a script the skill runs step-by-step). Keep the `playbook-updater-proposer` role only for Phase 5's per-task edit proposals, still dispatched from the now-root skill session with plain unnamed `Agent` calls.

**Added — a concrete, already-proven implementation template exists in this same `~/.claude/` config.** `~/.claude/skills/code-review-team` (Step 3) and the `tpx-sdlc` plugin's `reviewer-agent` (Phase 1) both already implement "assigned specialists dispatched in parallel via plain unnamed `Agent` calls batched into a single message, each finding passed through an independent adversarial validator before being reported" — directly matching the no-name-for-fire-and-forget convention cited in the Source section above. `tb:code-review-team` is invoked as a root-session skill (`/tb:code-review-team`), so its parallel fan-out is a working, in-repo precedent for what Phase 3 could become under Strategy 1: instead of the old arbitrary `sweep-batch-a/b/c` chunking, assign one specialist per playbook page or concern, dispatch them as unnamed calls in a single message from the (now-root) skill session, and run each surviving finding through one adversarial validator pass before Phase 4 task creation — reusing `code-review-team`'s Step 4.5 validator pattern rather than designing verification from scratch.

**Caveat — this precedent does not extend to non-root dispatch.** `tpx-sdlc`'s `reviewer-agent` (Phase 1) implements the identical unnamed-fan-out shape from a *non-root* context — it is itself spawned via the `Agent` tool, not run as a root-session skill — which is architecturally the same combination (non-root dispatcher + unnamed calls) as `playbook-updater`'s own original, already-disproven Phase 3 design (Source section above; `agent-stall-2026-08-25-diagnostic.md:7`). `reviewer-agent` has not been observed to stall the way `playbook-updater` did, but nothing in this task's research confirms it's actually reliable either — it may simply not have been stress-tested against this failure mode yet. This is outside CBP-457's scope (a different agent, unrelated to the FSAD Playbook), but is noted here because it bears directly on how much weight the precedent above should carry: it's proven for root dispatch, not for non-root, which is the same distinction this whole task turns on.

### Strategy 2 — Eliminate fan-out entirely; serialize the workflow

**What changes:** Stop depending on any multi-agent coordination primitive. `playbook-updater` (still spawned non-root, unchanged) performs Phase 3's HTML sweep and Phase 5's task execution itself, serially, in its own context — no `Agent` calls in either phase. Phase 5.5's independent verification becomes a distinct instruction block the *same* agent executes after an explicit context/attention-reset cue ("forget the edits you just made; now review this diff adversarially"), rather than a separately spawned verifier.

**What it fixes:** Removes the entire failure class outright — there is nothing to dispatch, nothing to wait on, nothing that can silently strand the run. This directly addresses 4 of the 5 documented incidents (2026-08-07, both 2026-08-24/25 attempts, and today), all of which were fan-out/coordination failures. Also the most direct answer to "the agent has become too complex" — the named-dispatch, active-polling, bounded-wait, and `STALLED`-status machinery all disappear.

**Tradeoffs:**
- Loses concurrency: the ~15-anchor-group sweep and multi-task execution become slower, serial passes.
- A single long-running context handling a large multi-task run (potentially 10–20+ CBP tasks) is more likely to hit its own context-window limits mid-run than several smaller sub-agent contexts would.
- Weakens Phase 5.5: self-review by the same agent that made the edits is a documented weaker check than independent review — the exact anti-pattern this project deliberately introduced a separate verifier to avoid (see Phase 5.5's own rationale in `playbook-updater.md`: "the agent making the edit is not a reliable judge of its own accuracy").
- **Added — drops a broader guardrail than "no concurrent-write risk" alone justifies.** `playbook-updater-proposer` is read-only by construction specifically so a single context can never both decide an edit and apply it unchecked — a guardrail distinct from, and broader than, the concurrent-write race that removing fan-out eliminates. Removing Phase 5's fan-out justifies dropping the *concurrent-write* risk, but Strategy 2 also removes the decide/apply separation itself: under this strategy, one context both decides every edit and applies it, with no structural check in between. That's a real tradeoff being accepted, not only the narrower one this plan names.

**Implementation sketch:** Rewrite Phase 3 as a straight loop over anchor groups (no batching), reading only the relevant HTML slice per group to manage context size. Rewrite Phase 5 as a straight loop over tasks, editing `fsad-playbook.html` directly (no `playbook-updater-proposer` role needed — there's no concurrent-write risk without fan-out, though see the guardrail-loss tradeoff above). Phase 5.5 becomes an explicit "adversarial re-read" instruction block run by the same agent after Phase 5 completes.

### Strategy 3 — Keep fan-out, but signal completion via the filesystem instead of any messaging primitive

**What changes:** Keep the named-sub-agent fan-out design for **Phase 3 and Phase 5.5 only** (see the Phase 5 caveat below — this mechanism does not work there), but stop relying on *any* live cross-session signal (`Agent` completion notifications, `ListAgents`, and `notify_when_idle` — confirmed unavailable to a non-root dispatcher; `SendMessage`'s reply-to-a-message path specifically has **not** been independently verified either way, per the Source section above — **corrected**, this strategy previously overstated it as "shown unreliable"). Each sub-agent's last action is to `Write` its result to a run-namespaced file (e.g. `markdown/updates/.run-<timestamp>/<batch-name>.json`) instead of, or in addition to, returning it as a message. The orchestrator detects completion by checking for file existence via its own `Bash`/`Read` tools — which every agent instance has, at any spawn depth, with no scoping caveats found in this project's testing so far — bounded by a single `Bash`/`Monitor`-driven wait loop rather than a model-turn-driven `ListAgents` poll loop.

**What it fixes:** Sidesteps the repeatedly-moving target of "which cross-session primitive is available to a non-root agent this week" by depending only on `Bash`/`Write`/`Read`, which are confirmed universally available. Avoids burning a full model turn per status check the way looping on `ListAgents` would (if it were even available).

**Tradeoffs:**
- Introduces filesystem coordination/cleanup concerns: a killed run (like today's) can leave stale result files that a later run could misread as instant completion — mitigated by the run-timestamp namespace, but adds moving parts.
- Still needs a bounded-timeout-then-`STALLED` fallback for a genuinely crashed sub-agent — same as today, just with a different completion signal, so it doesn't reduce structural complexity as much as Strategy 2.
- **Unverified assumption to check before implementing:** the `Bash` tool's own guidance discourages blocking `sleep` loops and prescribes the `Monitor` tool for "poll until a condition is met." Whether `Monitor` (like `Workflow`, `ListAgents`, and `notify_when_idle` before it) is actually available to a non-root spawned agent instance has **not** been confirmed and must be checked via `ToolSearch` from within an actual `playbook-updater` execution context before this strategy ships — repeating the same "assumed available, wasn't" mistake with a fourth primitive is the single biggest risk to this option.
- **This mechanism is structurally impossible for Phase 5 as currently designed, corrected from an earlier version of this strategy that claimed otherwise.** Phase 5 dispatches via the `playbook-updater-proposer` subagent type, which is deliberately given **no `Write`/`Edit`/`Bash` tool access at all** (`playbook-updater.md:178`) — that's the mechanism by which "return a proposed edit, don't write directly" is enforced, not an incidental restriction. A proposer sub-agent literally cannot `Write` a completion-signal file. Adopting this strategy for Phase 5 would require either granting the proposer role `Write` access — which undoes the exact structural guarantee Phase 5 exists to provide — or leaving Phase 5 on a different, separately-designed completion signal not sketched here. Strategy 3 is therefore only a Phase 3 / Phase 5.5 strategy as written; it does not cover Phase 5, which is a further reason it is not recommended as a first move over Strategy 2 (which removes Phase 5's fan-out entirely and sidesteps this problem).

**Implementation sketch:** Sub-agent prompt: "as your final action, `Write` your findings JSON to `markdown/updates/.run-<timestamp>/<batch-name>.json`, then produce your normal final-text summary as before." Orchestrator dispatches, then runs one bounded wait (via `Monitor` if confirmed available to it, else a `Bash` `until [ -f ... ]; do sleep N; done` loop wrapped in an explicit timeout) until all expected result files exist or the bound elapses, then `Read`s each file directly rather than relying on any message being delivered back.

### Recommendation

**Strategy 2 (eliminate fan-out), with Phase 5.5 *and everything gated on it* hardened by Strategy 1's mechanism**, is the recommended direction. (This revises the hybrid design below in response to `tb:plan-review` — see `task-cbp-457-review.md` — which found the original version of this section unimplementable; the corrections are called out inline.)

- It's the only option that removes the failure class by deletion rather than by substituting a different unverified primitive — directly answering the user's complaint that the agent's behavior "has become too complex." Every incident since 2026-08-07 has been the same category of coordination bug wearing a different mechanism; the pattern strongly suggests the fix is to stop needing coordination, not to find the coordination primitive that finally works.
- Its main weakness — losing independent, fresh-context Phase 5.5 verification — is mitigated by extending Strategy 1's "make the dispatcher root" idea to cover **Phase 5.5 together with everything Phase 5.5 gates, not the verifier dispatch in isolation.** Concretely: `playbook-updater` (non-root, Strategy 2, serial) runs Phases 0–5, then ends its turn by reporting its diff back to the *root* `cbp-update` skill session. That root session — not `playbook-updater` — then owns Phase 5.5 (spawns the single verifier, receives its PASS/FAIL verdict) **and Phase 6/7** (version bump, CHANGELOG, branch/commit/PR/auto-merge), gated directly on that verdict, all within the root session's own single continuous turn.
  - **Corrected — why Phase 6/7 has to move too, not just the verifier:** the current design gates Phase 6/7 on Phase 5.5 *inside the same `playbook-updater` invocation* (`playbook-updater.md:200,223`). If only the verifier dispatch moves to the root skill session while `playbook-updater` keeps Phase 6/7, then by the time the skill spawns the verifier, `playbook-updater`'s own turn has already ended — nothing resumes it to act on the verdict, so Phase 6/7 either never runs or runs ungated. Moving the gate and everything it gates into the same (root) session together is what keeps the gate functional.
  - **Corrected — the justification for why a root single dispatch is safe:** the discriminating variable across every incident in this task's own history is **root-ness of the dispatcher, not fan-out vs. single dispatch.** Phase 5.5's verifier dispatch on 2026-08-24/25 was already a single, non-fanned call, and it failed identically to the fanned Phase 3 batches — because both were dispatched by `playbook-updater` itself (non-root), not because of how many sub-agents were involved. No incident in the record tested a *root* session's own dispatch failing; root-dispatched fan-out is this project's normal, repeatedly-working convention (including throughout this very review). But a root-dispatched **single** verifier call specifically has not yet been exercised end-to-end in this project before being relied on here — it should be smoke-tested once, in isolation, before Phase 5.5 depends on it in production, rather than assumed safe by extrapolation from fan-out working.
  - **Caveat carried forward, not dropped (see Strategy 1's Tradeoffs, corrected):** this hybrid's root-dispatch mechanism is confirmed only for an interactive top-level session. No live scheduled/unattended `RemoteTrigger` routine currently exists in this repo to test root-ness against — the only scheduled-invocation artifact found is a stale, non-functional `launchd` job unrelated to `RemoteTrigger`. **Before this hybrid is relied on for any future scheduled/unattended invocation, the invoking session's root-ness must be independently confirmed** (e.g. via `ToolSearch` for `ListAgents`/`notify_when_idle` from within that session) — do not assume it transfers from the interactive case just because this document recommends it.
- Strategy 1 in full is the most architecturally correct long-term direction but is a larger, riskier rewrite (folding the entire phase spec into the skill) for a first fix; it's worth revisiting in full if the hybrid above still proves fragile.
- Strategy 3 is not recommended as a first move — it repeats this project's exact recurring mistake (assume a coordination-adjacent tool is available to a non-root agent) with `Monitor`, doesn't cover Phase 5 at all (see Strategy 3's corrected Tradeoffs), and even where it does apply, is more moving parts than Strategy 2 for the same net benefit.
- **Added — disposition of `playbook-updater-proposer`.** Under the Recommendation, Phase 5 is serial (Strategy 2, no proposer role) and Phase 5.5's verifier is a distinct role from the proposer — so `playbook-updater-proposer` is no longer invoked anywhere. The follow-on implementation task should delete `~/.claude/agents/playbook-updater-proposer.md` as part of adopting the Recommendation, rather than leave an unused, spawnable agent definition on disk.
- **Added — the code-review-team precedent strengthens, but doesn't change, this recommendation.** `playbook-updater` could adopt `tb:code-review-team`'s assigned-specialist pattern (see Strategy 1's Implementation sketch, corrected) — it's a good structural fit for Phase 3's sweep, but only under root dispatch. It does not fit Strategy 2, which deliberately removes fan-out from `playbook-updater` precisely because `playbook-updater` is non-root; grafting specialist fan-out back on would resurrect the failure class Strategy 2 exists to eliminate. Adopting the pattern would mean moving Phase 3 to the root skill session too, not just Phase 5.5/6/7 as the hybrid above does — this is an argument for treating Strategy 1 as a nearer-term revisit once it now has a concrete implementation template, not a reason to change today's recommendation.
- **Added — explicit approval gate before implementation.** This document is planning-only (see AC-05); nothing here should be read as pre-approving a follow-on task to implement the Recommendation without a human comparing the 3 strategies first. Given this repo's `CLAUDE.md` already establishes "check in before starting implementation" as the norm for non-trivial work, and that `playbook-updater`'s own Phase 7 auto-merges without further human review once triggered, the follow-on implementation task must be explicitly approved by the repo owner before it starts — it should not be picked up and shipped on the strength of this document alone.
