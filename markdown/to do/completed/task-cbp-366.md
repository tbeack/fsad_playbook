# CBP-366 — Implement the CBP-365 fix plan: synchronous Phase 3/5 dispatch, external liveness check, read-only Phase 5 sub-agent tools

## Source
Follow-up to CBP-365's diagnostic (`markdown/updates/cbp-365-diagnostic.md`), itself triggered by a live `/cbp-update` incident on 2026-08-07 where the `playbook-updater` orchestrator dispatched all 21 tasks correctly, then fabricated narration claiming 3 of its 6 Phase 5 batches had returned before it actually had them, self-corrected, then stalled for ~15 minutes without ever writing anything before its run simply ended.

## Summary
CBP-365 root-caused the incident directly against the orchestrator's own transcript (not inference) and produced a 5-item fix plan. This task implements that plan in the live agent definition (`~/.claude/agents/playbook-updater.md`), consistent with the precedent CBP-340 → CBP-342 set.

## Assessment
Full findings, transcript evidence, and reasoning are in `markdown/updates/cbp-365-diagnostic.md`. Summary of what needs to change in `~/.claude/agents/playbook-updater.md`:

- **Phase 3 (lines ~125–146) and Phase 5 (lines ~167–212)** currently read as if `Agent` calls block ("Collect all sub-agent findings before proceeding"), but never set `run_in_background: false` — the tool defaults to async/background dispatch, which is what let the orchestrator narrate fabricated "batch back" status during genuine multi-turn waiting (CBP-365 Finding 1/2).
- **Success Criteria (lines ~292–299)** only cross-checks Phase 2's release-delta list against completion outcomes reported at the end of a run — it cannot catch a run that never reaches its own "before reporting completion" step, which is exactly what happened (the orchestrator's transcript stalls and simply ends).
- **Phase 5's sub-agent instructions** ask sub-agents to "return a proposed edit... rather than writing to `fsad-playbook.html` directly," but this is instructional only — nothing in their tool access structurally prevents a direct write (observed during this incident's manual recovery).
- **`SendMessage`** is never mentioned anywhere in the spec, yet 3 of 6 dispatched sub-agents in the 2026-08-07 run reached for it anyway (2 completed a failed call to an unregistered name, 1 loaded the tool but never called it) — a predictable improvisation once async dispatch leaves a sub-agent with no reliable way to signal completion to a non-root parent.

## Plan

1. **Force synchronous dispatch (primary fix).** Add `run_in_background: false` to every Phase 3 and Phase 5 `Agent` call in the spec's instructions. Update the surrounding prose so it explicitly states this requirement rather than only implying synchronicity through "collect before proceeding" phrasing. This structurally prevents the confirmed root cause (CBP-365 Finding 1/2) — a blocking call's result is a real tool_result in the transcript, leaving no gap for the orchestrator to narrate a fabricated completion into.
2. **Restrict Phase 5 sub-agents to read-only tool access** (`Read`, `Grep`, `Glob` — no `Write`/`Edit`, no `Bash`) when dispatching them, so "return a proposed edit, don't write directly" is enforced by what tools are available, not just by instruction. Confirm this is expressible with however Phase 5's sub-agent dispatch is actually invoked (custom `agentType`/tool-restriction mechanism, matching the pattern already used by several existing agent definitions in this environment).
3. **Extend the Success Criteria section (lines ~292–299) with a Phase 4→Phase 5 completeness check**: before a run reports completion, cross-check every CBP task created in Phase 4 against either an applied-and-verified edit or an explicit reason logged under a new `## Execution Gaps` subsection in the daily report (`markdown/updates/YYYY-MM-DD.md`), parallel to Phase 4a's existing `## Deferred` section.
4. **Add an external liveness/timeout check** at whatever level invokes the `playbook-updater` agent (the `/cbp-update` skill and/or the cloud routine's own scheduling wrapper, if one exists) — since a self-administered Success Criteria check (item 3) cannot catch a run that never reaches its own end. Concretely: if the agent hasn't produced a commit or a clear terminal status within a defined timeout window of dispatch, treat the run as stalled and surface that explicitly, rather than relying solely on the orchestrator to notice and report its own failure to progress. This is a second, independent layer on top of item 1, not a replacement for it — even with fully synchronous internal dispatch, the orchestrator's own top-level run could still hang without returning.
5. **Verify end to end.** After implementing 1–4, confirm the spec file's Phase 3/5 language explicitly names the dispatch mechanism (no ambiguous "collect before proceeding" phrasing left unqualified), and that the new Execution Gaps / liveness-check instructions are concrete enough to act on directly from the spec text alone.
